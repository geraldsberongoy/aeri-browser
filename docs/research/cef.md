## Method and probes actually run

- Cloned `chromiumembedded/cef` master (`e6035cf`, 2026-11-12, Chromium 158.0.8127.0) and branch `8078` (CEF 156, tip `e603d97`, 2026-11-17) to /tmp; read headers, `libcef`, patches, docs.
- Read Chromium source at tag `156.0.8078.96` via gitiles (extension service, devtools handler, webauthn, paths).
- Cloned `tauri-apps/cef-rs` (HEAD `b84b7ca`, 2026-11-15) and read it.
- Downloaded the prebuilt `cefclient.app` from the Spotify CDN (`cef_binary_156.0.30+g6028375+chromium-156.0.8078.96_macosarm64_client`, 129 MiB, macOS arm64, ad-hoc signed, no entitlements) and drove it with CDP (`--remote-debugging-port`) in three modes: **Chrome style** (`--use-views`, the default), **Alloy style in a native NSView** (`--use-native`; cefclient logs "Native parent on MacOS requires Alloy style"), and a plain Chrome-style CWS page. A tiny MV3 test extension (`content_scripts` at `document_start`, a `declarativeNetRequest` static block rule, a service worker, `nativeMessaging`) and a stdio native-messaging host were loaded with `--load-extension`.
- Probe limits: I could not press the CWS "Add extension" confirmation (no Accessibility permission; my synthetic click instead raised macOS permission prompts for the host terminal app, see the note in the final message). **Install completion from the CWS is therefore not verified**; the install prompt itself is.
- Everything below the probes is single-run, single-machine (Apple Silicon, macOS 27). No memory/CPU benchmarks were taken.

## Headline findings

1. **Alloy-style (native NSView) browsers run `--load-extension` MV3 extensions: content scripts, DNR blocking and native messaging all worked in my probe**, but `chrome.tabs.query` returned `[]` and `chrome.windows.getAll` returned 0 windows, and there is no extension UI (action, popup). The "content scripts in Alloy are unverified" gap in the secondary note is closed: Observed working.
2. **Chrome Web Store install works only with a Chrome-style browser** (Observed: `chrome.webstorePrivate` present on the CWS page and the native "Add 'uBlock Origin Lite'?" dialog opened). **On macOS Chrome style cannot be hosted in a parent NSView** (Observed in source, issue #3294 still open). So "GPUI window + embedded CEF NSView + CWS install" is not available today.
3. A separate **runtime-install path exists via DevTools protocol** (`Extensions.loadUnpacked`, Observed working with two flags), but it is unpacked-only, loads into one default context, and did not persist across restart.
4. **Standard CEF builds lack H.264/AAC and Widevine** (Observed in probe: `canPlayType` empty, `requestMediaKeySystemAccess` fails). This hits "Chrome web compatibility" independently of extensions.
5. **Passkeys:** the macOS platform authenticator needs the Apple-restricted entitlement `com.apple.developer.web-browser.public-key-credential` on the Aeri main executable (Observed: Apple doc, Chrome's entitlements). The probe app, without it, reports no platform authenticator in either style.

- Net cost of tracking CEF (Inferred): monthly Chromium security updates mean Aeri must ship a new `Chromium Embedded Framework.framework` roughly monthly on stable, or ~6-monthly on LTC/LTS hops; code changes are small if the API pin is held, behaviour regressions are the real cost.

**Licences.**

CEF docs ask apps to ship the licence text, e.g. on an About page; `about:license` and `about:credits` exist inside a CEF browser (Observed [7] `general_usage.md`).
- Chromium: BSD-3 plus bundled third-party code. The `CREDITS.html` shipped in the 156 mac client dist is 5.3 MB with 492 product entries (my parse); 17 entries mention an LGPL licence, including **ffmpeg, libusbx, gtk, libsecret, libbrlapi, WebKit portions** (Observed, my regex over the file; exact per-platform lists differ). **Inferred obligation:** ship the credits/notice file with the app and keep it per-build; FFmpeg's LGPL means Aeri must not statically strip or obscure the ability to replace the library: standard CEF ships it inside the framework dylib, so Aeri's exposure is the same as any CEF app (legal review is outside this scope).
- **Codecs/DRM (Observed):** Google's CEF build instructions state "CEF's default build does not enable proprietary audio and video codecs"; enabling needs `ffmpeg_branding=Chrome proprietary_codecs=true` and "licensing agreements with and fees paid to … patent holders" [8]. My probe on the standard 156 build: `canPlayType('video/mp4; codecs="avc1.42E01E"')` = `""`, `audio/mp4; mp4a.40.2` = `""`, `MediaSource.isTypeSupported` H.264 and HEVC = false; VP9, AV1 and MP3 = "probably"; `requestMediaKeySystemAccess('com.widevine.alpha')` rejected "Unsupported keySystem". So H.264/AAC sites, Netflix-style DRM and some conferencing paths need either a custom CEF build (patent licensing) or are unsupported. This is a real "Chrome compat" gap that is independent of the stack decision and not covered by the requirements doc.

## 3. Runtime styles

**Today (Observed [12] `cef_types_runtime.h`, master; same text in 8078).** Since M128 (#3685 closed 2024-07-01 [13]) there is only the **Chrome bootstrap**; "style" is per window/browser: *Chrome style* = full Chrome UI layer (toolbar, dialogs, extensions, passkey/permission UI), *Alloy style* = content layer, fewer features but more client callbacks and support for windowless rendering. Rules from the header: windowless always Alloy; a Chrome-style Views `CefWindow` may host Alloy `BrowserView`s, but an Alloy Window hosts only Alloy; a Chrome Window hosts at most one Chrome BrowserView.

**Source verification (Observed, `libcef/browser/browser_host_create.cc` @ branch 8078 `e603d97`, `CefBrowserCreateParams::MaybeSetWindowInfo`).**
```
if (allow_chrome_style && new_window_info.windowless_rendering_enabled) allow_chrome_style = false;  // windowless
#if BUILDFLAG(IS_MAC)
if (allow_chrome_style && chrome_child_window::HasParentHandle(new_window_info))
    allow_chrome_style = false;   // "Chrome style is not supported with native parent on MacOS. See issue #3294."
#endif
```
`HasParentHandle` is `window_info.parent_view` on macOS and `parent_window` elsewhere (`libcef/browser/chrome/views/chrome_child_window.cc`). `cef_types_mac.h`: "Alloy style will always be used if |windowless_rendering_enabled| is true or if |parent_view| is provided." Issue #3294 "chrome: Add support for embedded non-Views windows" is **open** (last update 2024-08-05) [14].

| macOS embedding | Resulting style | Evidence |
|---|---|---|
| (a) Windowed into your `NSView` (`parent_view`) | **Alloy**, forced even if CHROME is requested (an error is logged and style reset) | source above; cefclient log "Native parent on MacOS requires Alloy style … Using Alloy style; Native-hosted window" (probe) |
| (b) Off-screen rendering (`windowless_rendering_enabled`) | **Alloy**, always | `cef_types_runtime.h` + `MaybeSetWindowInfo` |
| (c) CEF Views (`CefWindow` + `CefBrowserView`) | **Chrome (default)**; Alloy selectable via `GetWindowRuntimeStyle`/`GetBrowserRuntimeStyle` | header; cefclient default `--use-views` showed `browser_ui` targets (omnibox popup, WebUI) in CDP = Chrome UI layer present |

Windows (Inferred from the same code, not tested): Chrome style *can* take a parent HWND because `HasParentHandle` only blocks on macOS (`chrome_child_window.cc` creates a Views `ChildWindowDelegate` under the parent). So the mac-specific gap is real and Windows would differ.

**Chrome-style Views details relevant to a custom UI (Observed).** `CefBrowserViewDelegate::GetChromeToolbarType` returns `CEF_CTT_NONE` by default (no Chrome toolbar), `CEF_CTT_LOCATION` or `CEF_CTT_NORMAL` (`chrome_browser_view.cc:OverrideCreateToolbar`). `CefWindowDelegate::IsFrameless`, `WithStandardWindowButtons`, `GetTitlebarHeight` (mac) exist. On macOS `CefWindow::GetWindowHandle()` returns the `NSWindow`'s **contentView** (`view_util_mac.mm`), so an app can reach the `NSWindow` behind a Chrome-style Views window. `CefBrowserHost::ExecuteChromeCommand/CanExecuteChromeCommand` are Chrome-style only (`cef_browser.h`). `CefWindow::AddOverlayView` adds **Views** overlays only.

### 4.2 Runtime-install routes

- **CEF API:** none. `CefRequestContext::LoadExtension`, `CefExtension`, `CefExtensionHandler` were removed in M128 ("The extension API as it currently exists … will be removed in #3685", magreenblatt 2024-05-03, #3450 [21]; `include/` at 8078 contains no `cef_extension*.h`). #3877 "Add API to load extension during runtime (pref change not enough)" is **open**; maintainer's only suggestion (2025-03-21): listen for the pref change inside CEF [20]. #3450 "programmatic extension management" is **open** [21].
- **Pref write:** writing `extensions.settings` via `CefRequestContext::SetPreference` works only after restart (reporter, #3877 [20], Reported).
- **CDP `Extensions.loadUnpacked` (Observed, my probe):** with `--remote-debugging-port=<p> --enable-unsafe-extension-debugging`, a browser-target WebSocket call `Extensions.loadUnpacked {path}` returned the extension id; `Extensions.getExtensions` listed it; after `Page.reload` the content script and DNR rule applied. After restarting cefclient on the same cache dir, `getExtensions` returned `[]`, i.e. **not persisted** (the `getExtensions` doc says it lists unpacked extensions; persistence of CDP-installed ones was not otherwise checked). Source (Chromium 156.0.8078.96 `chrome/browser/devtools/protocol/extensions_handler.cc`): `LoadUnpacked` only runs when the handler is on the *browser* target and unsafe operations are allowed, and it installs into `DevToolsBrowserContextManager::GetDefaultBrowserContext()` with `installed_via_cdp`; **it is not addressable per CEF profile** (Inferred from that call; per-profile behaviour untested). `Extensions.triggerAction {id, targetId}` requires a tab target, resolves `BrowserWindowInterface` via `browser_window_util::GetBrowserForTabContents` and dereferences `ExtensionsContainer::From(*browser)` and `GetActionForId` **without null checks** (read in the same file), so it is Chrome-style only, and a Chrome-style window with `CEF_CTT_NONE` may lack the container (Inferred; untested). Opening a debug port also exposes a local control plane (security consideration, Inferred).
- **Upstream proposal:** PR #4187 "feat: add new Extensions API for Alloy and Chrome runtimes" by CrabNebula (Tauri), 26 files, +3,319 lines, adding `cef_extension.h`, `cef_extension_handler.h`, `extension_popup_manager`, `extension_action_impl`, a demo test, and edits to `chrome_browser_extensions.patch`; **closed unmerged 2026-06-03**, no description or review comments [22]. It shows (a) the demand, (b) a restored extension API would need patches to Chromium's extension code, i.e. a custom CEF build. Its function was not verified.
- **Chrome Web Store install from a script, not UI:** not found in any CEF source or issue (grep of `libcef`/patches/tests for `webstore` returned nothing). Using Chrome's own CWS flow (Chrome style) is the only observed route.

### 4.3 MV2

Observed: Chrome doc [23]: MV2 disabled for all users in Chrome 138 (2025-07-24), enterprise policy removed in 139, all remaining MV2 extensions removed from the Web Store 2026-08-31. Chromium source: at `150.0.7871.115` `extensions/common/extension_features.cc` has `kExtensionManifestV2Unsupported` (enabled by default) and `kAllowLegacyMV2Extensions` (disabled by default); at `156.0.8078.96` and `158.0.8127.18` the MV2 feature flags are **absent** from that file (grep `mv2|ManifestV2` returns nothing; `manifest_v2_experiment_manager.h` is 404 at 150, 156 and 158). So MV2/classic uBlock Origin is not available in current CEF; **uBlock Origin Lite (MV3, DNR)** is the realistic extension. (Which constraints MV3/DNR impose, e.g. rule counts, belongs to the blocking research.)

### 4.4 Architecture options

Facts that drive the options (all Observed above): (i) CWS install and extension action UI need a Chrome-style Browser; (ii) on macOS Chrome style is Views-only (no `parent_view`); (iii) Alloy runs extension background pages, content scripts, DNR and native messaging but has no tabs/windows model and no UI; (iv) `CefWindow::GetWindowHandle()` on mac gives the `NSWindow` contentView; (v) renderer content is hosted by Chromium's GPU process and the window is a Views-owned NSWindow.

| Option | Feasible? | Evidence | Cost / risk |
|---|---|---|---|
| **A. Alloy browsers in GPUI's NSView + Aeri's own extension shell**: preload/CWS-fetched extensions, content scripts + DNR + SW via Chromium, Aeri implements install flow, permission prompt, action UI | **Partly.** Runtime of extensions: yes (probe). Install from CWS, popups, `tabs/windows` surface: **no without patches** | Probe results; #4011/#4255/#4256 maintainer statements ("no plans for general-purpose Tab API support with Alloy style", #4011 2025-10-06 [24]); `GetAlloyTabById` only | High: Aeri would need its own CRX download/verify/unpack (CWS update-URL protocol, CRX3 verification), `Extensions.loadUnpacked` or `--load-extension` (restart-only), popup hosting (popups are `chrome-extension://` pages Aeri would have to open in its own Alloy browser and wire `chrome.action`), and a window/tab model that `chrome.tabs/windows/scripting/commands` extensions (1Password, Bitwarden, dark-mode) expect. Requirement "install from Chrome Web Store page or link, genuine package check" must be re-implemented. Not recommended |
| **B. Chrome-style Views window (frameless, `CEF_CTT_NONE`), GPUI UI in separate overlay `NSWindow`s ("child windows") ordered above it** | **Plausible, untested.** | Views windows can be frameless and expose the NSWindow (`IsFrameless`, `GetWindowHandle`); `GetChromeToolbarType` lets Chrome UI be dropped; native macOS child windows over another app window are a standard AppKit capability (Inferred); CWS prompt and popups come from Chrome UI. Still no popups/actions for Alloy tabs and no tab/windows model; popup UI would be a Chrome-style window. Inferred: unusual, fragile |
| **E. Carry a CEF patch** (revive an extension API like PR #4187, or add Chrome-style-in-NSView, issue #3294) and self-build CEF | Technically yes | #4187 exists as a prior art; #3294 open since 2022 (24 comments) | Very high: you own a Chromium+CEF build pipeline, per-milestone rebases (~monthly); close to the "fork" non-goal and the largest ongoing cost. Would also be the route to enable H.264/Widevine |
| **F. Windows-style child embedding on Windows only** (Chrome style with parent HWND) | Likely on Windows | `HasParentHandle` only blocks on macOS | Doesn't solve macOS-first |

## 5. Profiles

**Isolation rules (Observed, `cef_types.h` and `libcef/browser/chrome/chrome_browser_context.cc` @ 8078).**
- `CefRequestContextSettings.cache_path` non-empty must be an absolute path equal to or a **direct child** of `CefSettings.root_cache_path` (code: `cache_path_.DirName() == user_data_dir`; anything else logs "Cannot create profile at path" and falls back to a new OffTheRecord profile). Equal to `root_cache_path` = the default/primary profile; empty = "incognito" in-memory (an OTR profile of the primary one). Settings fields like `persist_session_cookies`, `accept_language_list` are ignored when `cache_path` equals the global one.
- With the Chrome bootstrap each disk context is a **full Chrome `Profile` created through `ProfileManager::CreateProfileAsync`** (`InitializeAsync`). Inferred consequence: the per-profile overhead is Chrome's profile object graph (KeyedServices, prefs, history/cookie DBs, extension registry/service, content-settings map). I found no primary measurement of the cost; it must be measured.
- Root cache path process singleton: "A process singleton lock based on the root_cache_path … applies to all CEF-based applications using version 120 or newer"; implement `CefBrowserProcessHandler::OnAlreadyRunningAppRelaunch` (Observed `cef_types.h`). Multiple Aeri instances on one root path are therefore blocked, which matches "one app process tree" but means Aeri's own profile data must live elsewhere.
- Cookies/cache/localStorage/IndexedDB: Chromium partitions storage by `BrowserContext`/`StoragePartition`; Chromium's process-model doc states two documents from different profiles or StoragePartitions "can never share the same renderer process" ([26] `process_model_and_site_isolation.md` @156.0.8078.96, Process Reuse) (Observed for process separation; storage separation is Chromium's standard design, Inferred-from-architecture for each store, to be confirmed by the spike).
- Shared process tree (Observed in my probe with one profile: browser, one GPU process, a **network-service utility process** and a **storage-service utility process** plus renderers/extension processes). Chromium design (`services/network/README.md` @156 [27]): one network service (out-of-process on desktop) with many `NetworkContext`s, so N profiles do **not** multiply the browser, GPU or network processes (Observed for the single-service design; multi-profile process count unmeasured). Renderers are per-profile: the same site open in 5 profiles = 5 renderers (Observed rule [26]); extensions also get separate processes per extension per profile (Inferred: `Extensions` section of [26] plus per-profile registries).
- Permissions: `CefPermissionHandler` is obtained from the **`CefClient`** (per browser), not per request context. In Chrome style default handling shows Chrome's prompt UI, which stores decisions in that profile's content settings (Inferred); in Alloy style default is `CEF_PERMISSION_RESULT_IGNORE` (Observed `cef_permission_handler.h`). So Aeri must implement per-profile permission decisions in its own client and key them by the browser's request context if it wants a unified UI.
- `CefRequestContextHandler` adds per-context `GetResourceRequestHandler` (a second interception layer) and `OnRequestContextInitialized`; `CefRequestContext` exposes `ClearCertificateExceptions`, `ClearHttpAuthCredentials`, `CloseAllConnections`, `SetPreference/GetPreference` (Observed `cef_request_context.h`).
- Dormant profile (no browsers): `ChromeBrowserContext::Shutdown` resets the profile keep-alive and lets `ProfileManager` unload it; whether memory returns to baseline is **unmeasured**.

## 6. Process model and resource control

- Process model (Observed [26]): desktop uses full site-per-process; process limit is soft and based on available memory; **different profiles never share a renderer**; extensions don't share processes with pages or each other and are capped at one-third of the soft limit in the count. CEF's own doc still says "a new render process for each unique origin" ([7], stale/coarser than the above).
- Discarding/freezing: **No CEF API exists** (grep of `include/` for `discard|freeze|Discard|Freeze` found only unrelated hits; `include/cef_browser.h` has `WasHidden`, but its docs say "This method is only used when window rendering is disabled", i.e. OSR). There is no memory-pressure API either.
- Hide/occlusion for windowed browsers: relies on Chromium's native view/window visibility handling (Inferred); no CEF docs promise throttling. Needs a spike (hide the NSView or occlude the window; observe renderer CPU and `document.visibilityState`).
- Chrome-style Chrome machinery: the Chrome layer's tab lifecycle ("Memory Saver"), performance manager and `chrome.tabs.discard` are tied to `TabStripModel`/`TabLifecycleUnitExternal`. In Alloy, maintainer analysis for #4256 (2026-09-09) states the lookup returns "a WebContents without a Browser/tab-strip entry, so it has no TabLifecycleUnitExternal" [17] (Observed). So **Alloy tabs cannot be discarded by Chrome's own mechanism**; for Chrome-style it is plausible but untested (Inferred; relevant pref `performance_tuning.high_efficiency_mode.state` is a guess to test).
- Aeri-implemented "rest" is simple and reliable: record `CefBrowserHost::GetNavigationEntries` (Observed API, `cef_browser.h:669`) and URL/title/favicon in Aeri's model, `CloseBrowser`, recreate on first show (no API to restore a navigation entries list in `include/` grep; reload from the current URL). Unsent form input is lost unless captured via JS first.
- Per-browser resource reads (Observed `include/cef_task_manager.h`, `cef_types.h`): `CefTaskManager::GetTaskManager()` (UI thread) → `GetTaskIdsList`, `GetTaskInfo(id)` → `{type, title, cpu_usage (0..n_cpu*100%), memory (bytes footprint, -1 if unavailable), gpu_memory (with a `is_gpu_memory_inflated` flag for the aggregate GPU process), is_killable}`, `GetTaskIdForBrowserId(browser_id)`, `KillTask`. This is exactly the data Chrome's task manager shows; it covers browser, GPU, renderer and (inferred) extension tasks. `OnRenderProcessUnresponsive/Responsive` are in `CefRequestHandler`; `CefBrowserHost::IsRenderProcessUnresponsive` exists. `chrome_browser_task_manager.patch` is in CEF's patches (Observed).

## 7. Network interception and cosmetic injection

**Interception (Observed `include/cef_resource_request_handler.h`, `libcef/browser/net_service/`, `chrome_content_browser_client_cef.cc` @ 8078).**
- `CefResourceRequestHandler::OnBeforeResourceLoad` is "called on the **IO thread** before a resource request is loaded"; may modify/redirect (changing the URL is a redirect), return `RV_CONTINUE`, `RV_CONTINUE_ASYNC` (with `CefCallback`) or `RV_CANCEL`. `browser`/`frame` "may be NULL for requests originating from service workers or CefURLRequest". Handler is chosen per request via `CefRequestHandler::GetResourceRequestHandler` (browser level) then `CefRequestContextHandler::GetResourceRequestHandler` (context level); the first call is made on the same IO thread with `is_navigation`, `is_download`, `request_initiator` (Observed `cef_request_handler.h`).
- Mechanism: `ChromeContentBrowserClientCef::WillCreateURLLoaderFactory` installs a proxy `URLLoaderFactory` for profiles created by CEF; so it covers requests that go through the network service URL loader (navigations, subresources, XHR/fetch, service-worker script and fetch requests). Request types enumerated in `cef_resource_type_t` (`RT_MAIN_FRAME … RT_XHR`, `RT_WORKER`, `RT_SHARED_WORKER`, …). A grep of `libcef/browser/{net_service,chrome,alloy}` for `WebSocket` finds nothing: **WebSocket connections are not routed through this interception** (Inferred from absence; the `WillCreateWebSocket` content hook is not overridden in the files searched). Block lists that need to cancel `ws://`/`wss://` need a different layer (DNR in an extension covers `websocket` resource type in Chromium, not tested here).
- Per-request cost (Inferred, unmeasured): every request crosses the IO thread, builds a `CefRequest` wrapper plus handler refcounting; for a Rust handler add the FFI hop and a filter-engine match. Since the callback is synchronous on the IO thread unless `RV_CONTINUE_ASYNC`, the matcher must be allocation-light and lock-free; an async decision would cost a thread hop. Must be benchmarked on a page-load corpus.
- Interaction with extensions: CEF's proxy runs *in addition to* Chrome's own extension `webRequest`/DNR (the proxy is layered on Chrome's `WillCreateURLLoaderFactory`; also, the DNR block in my probe worked alongside CEF's proxy).
- `OnResourceResponse` response *modification* is not available (#2785 open).

**Cosmetic filtering / script+CSS at document start (Observed headers and source).**
- Renderer side: `CefRenderProcessHandler::OnContextCreated(browser, frame, context)` "called immediately after the V8 context for a frame has been created", before page scripts; `frame->ExecuteJavaScript` and V8 APIs are usable there. The renderer client exists for **both** styles (`libcef/renderer/chrome/chrome_content_renderer_client_cef.cc` and the common `render_frame_observer`). Early document may lack `documentElement`; CSS insertion needs `adoptedStyleSheets`/a `MutationObserver` or the first `DOMContentLoaded` (Inferred).
- Browser side: `CefRequestHandler::OnDocumentAvailableInMainFrame` (UI thread, main frame only) and `CefLoadHandler::OnLoadStart` (later) are weaker hooks; `CefFrame::ExecuteJavaScript` from the browser process is async.
- Extensions give a second, standard path: a bundled Aeri content-script extension (loaded with `--load-extension`) with `run_at: document_start` worked in both styles in my probe; uBO Lite's own cosmetic features would also ride this path.
- Style dependence: the render-process handler is supported in both styles (Observed files); per-frame injection into extension pages or `chrome://` is not Aeri's concern.

## 8. macOS embedding practicalities

- Message loop (Observed `cef_types.h`): `multi_threaded_message_loop` "is only supported on Windows and Linux". On macOS use `CefRunMessageLoop()` or `external_message_pump = true` with `OnScheduleMessagePumpWork` → `CefDoMessageLoopWork()` on the main thread; the header says external pump "is recommended for use in combination with the CefDoMessageLoopWork() function in cases where the CEF message loop must be integrated into an existing application message loop". Reference pump: `tests/shared/browser/main_message_loop_external_pump_mac.mm` uses a timer in common and event-tracking modes (so menus/live resize don't freeze web content) and a 33 ms max delay constant that is a sample choice (read earlier from master in [28]; unverified for 8078 by re-read). **GPUI integration is the open question**: GPUI/winit-style loops must call `CefDoMessageLoopWork` from the main thread and keep the run loop modes right; cef-rs's `osr` example sets `external_message_pump: true` [5].
- App-level macOS requirements (Observed in cef-rs `application_mac.rs` and cefsimple): the `NSApplication` subclass must implement `CefAppProtocol` (`isHandlingSendEvent`), and `terminate:` must be intercepted so browsers close first. GPUI's own `NSApplication` subclass would have to expose this (see GPUI research).
- Bundle layout (Observed, 156 `cefclient.app` listing and `README.redistrib.txt`): `Contents/Frameworks/Chromium Embedded Framework.framework` (Xcode 26 requires a versioned framework with `Versions/A` + `Current` symlinks), helper apps in `Contents/Frameworks`. The prebuilt 156 client ships **4** helper bundles (`Helper`, `Helper (Alerts)`, `Helper (GPU)`, `Helper (Renderer)`), while the CMake variable still lists `(Plugin)` as a fifth (`cmake/cef_variables.cmake.in:397-403`); in my probe the GPU and network/storage utility processes launched from the plain `Helper.app`, renderers from `Helper (Renderer).app`. Treat `Helper (Plugin)` as likely unused but keep the list identical to the shipped CMake variable until verified. Helper bundle IDs `…helper.renderer` etc., `LSUIElement=1`.
- Library loading/sandbox (Observed [29] `sandbox_setup.md`, `library_loader.h`): executables must load the framework at runtime (`cef_load_library`), not link it; from M138 `cef_sandbox` is `libcef_sandbox.dylib` in the framework `Libraries` dir loaded via `dlopen`, initialised in the helper before loading the framework; V2 sandbox since branch 3538. cef-rs wraps both (`LibraryLoader`, `Sandbox`).
- Hardened runtime/entitlements: CEF ships no entitlement templates (the Spotify cefclient is ad-hoc signed with none: `codesign -dv`: `flags=0x20002(adhoc,linker-signed)`). The reference is Chrome's own: `chrome/app/helper-renderer-entitlements.plist` and `helper-gpu-entitlements.plist` grant `com.apple.security.cs.allow-jit` (Observed in the secondary note; not re-fetched here, so **Reported**). Aeri must sign framework → helpers → app inside-out and test notarised builds (Inferred).
- Clean shutdown: normal path is `CloseBrowser` for every browser, wait for `OnBeforeClose`, then `CefShutdown`; cefsimple's mac pump drains with extra `CefDoMessageLoopWork` loops (Reported [28]). In my probe, `SIGTERM` to the browser process left **0** cefclient processes alive 4 s later (helpers exit when the browser dies; observed once for the Chrome-style run and again at the end of each probe). This is not a proof of clean data flush.
- Crash handling (Observed `cef_request_handler.h`): `OnRenderProcessTerminated(browser, status, error_code, error_string)` on the UI thread; "Aw, Snap" equivalent; `OnRenderProcessUnresponsive/Responsive` for hangs. GPU/utility crashes are not surfaced here (Inferred). `docs/crash_reporting.md` exists for Crashpad integration (not read).
- Notification side effect seen in probe: the cefclient browser asked macOS for notification permission under its own bundle ids (`cefclient.app`, `cefclient Helper (Alerts)`), so Aeri's bundle identity matters for notifications.

## 9. Passkeys / WebAuthn

- Observed (Chromium 156.0.8078.96): `chrome/browser/webauthn/chrome_authenticator_request_delegate.cc` contains iCloud Keychain and Touch ID handling; `device/fido/mac/icloud_keychain.mm` uses `AuthenticationServices` (`ASAuthorizationWebBrowserPlatformPublicKeyCredential…`) and requests system authorisation ("If the user authorizes Chromium then `platformCredentialsForRelyingParty` will start working").
- Entitlement (Observed): Chrome's `chrome/app/app-entitlements-chrome.plist` includes `com.apple.developer.web-browser.public-key-credential = true`, `com.apple.application-identifier`, `keychain-access-groups` with `<TEAM>.<BUNDLE>.webauthn`, `.webauthn-uvk`, and `com.apple.developer.associated-domains.applinks.read-write`. Apple's page for the entitlement (macOS 13.3+): lets an app "make registration and assertion requests for passkeys and security keys for any relying party identifier"; **you must be the Account Holder of an organisation account and apply via the form at developer.apple.com/contact/request/macos-browsers-passkeys**; Apple reviews against criteria (HTTP/HTTPS schemes in `Info.plist`, a URL field/search/bookmarks on launch, navigates directly and renders expected content) and then grants it as a managed capability [30]. So **yes, a CEF-based app can request it**; it goes on the Aeri main executable (the browser process), which is where the AuthenticationServices call happens.
- Touch ID authenticator (Observed code): `TouchIdAuthenticatorConfigForProfile` builds the keychain access group from compile-time `MAC_TEAM_IDENTIFIER_STRING "." MAC_BUNDLE_IDENTIFIER_STRING ".webauthn"`. Spotify CEF binaries are built with Google/CEF's values (Inferred), so this legacy path will not match Aeri's signing identity. The iCloud Keychain path (system API) has no such compile-time dependency in the file I read.
- CEF-specific (Observed): maintainer statements: WebAuthn dialogs "require use of the Chrome runtime" (#3508, 2023-05-17 [31]); Windows Hello "should currently work with the Chrome runtime … We will likely not support this with the Alloy runtime" (#3275, 2022-03-08 [32]); "If it is supported by Google Chrome then it should also work with CEF's Chrome runtime … test it on your OS" (#3505, 2023-05-13 [33]). Passkey UI sizing bug #3886 closed 2025-02-22 [34]. These are old; the style rule still stands because the dialogs are Chrome UI and Alloy has no Browser.
- My probe (Observed): in cefclient 156 (ad-hoc signed, no entitlement) `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()` returned `false` in **both** Chrome-style and Alloy-style (and `isConditionalMediationAvailable()` returned `true`). This does not prove an entitled app would work, only that the default CEF build gives no platform authenticator without it.
- Windows Hello: no entitlement; Chromium uses the Windows WebAuthn API. Not tested (macOS-first). **Inferred**: works with Chrome style only, per the maintainer notes above.
- Alloy-style conclusion (Inferred): passkey prompts need Chrome-style UI, so the Alloy-in-GPUI route needs Aeri to build its own passkey UI around `CefPermissionHandler`/(no public WebAuthn hook found in the headers) and likely cannot do so; I found no WebAuthn callback in `include/`.

## Implications for Aeri

1. **The architecture hinges on one trade-off the stack can't dodge on macOS:** Chrome-Web-Store install and extension popups need Chrome style, and Chrome style on macOS cannot live in a foreign `NSView`. Either (B/C) keep a Chrome-style CEF Views window as the host and layer GPUI around/over it, or (A) host Alloy browsers inside GPUI and re-implement the CWS install + action UI yourself. Option A re-implements a big piece of Chrome; B/C need a layering spike but keep CWS install, popups, passkey UI and permission prompts in Chrome code. I recommend spiking B (then C) first; do not pick Alloy-in-NSView as the base unless the requirement for CWS install is relaxed.
2. A cheaper, lower-risk hedge exists in the probe results: **Alloy runs the extension runtime (SW, content scripts, DNR, native messaging)**. If B proves unworkable, the fallback is "Alloy + Aeri-built install/UI" (A) with uBO Lite and a password-manager extension preloaded.
3. Plan on **one CEF-hosting process model with many `CefRequestContext`s** for profiles; they are full Chrome `Profile`s, so "each extra profile costs little" must be measured, not assumed. Same-site pages in different profiles will use separate renderers; process-level lightness depends on tab rest/discard, which CEF doesn't provide: Aeri must implement rest by closing/recreating browsers and use `CefTaskManager` for the resource view.
4. **Do not rely on CEF for WebSocket blocking or for response modification**; use DNR (extension) or Aeri-side logic. For built-in blocking use `OnBeforeResourceLoad` (IO thread) with a lock-free matcher and measure per-request latency; cosmetic filtering can use the renderer `OnContextCreated` hook or a bundled content-script extension.
5. **Codecs/DRM are a product decision:** standard CEF builds fail H.264/AAC/Widevine. Choices: accept the gap, or self-build CEF with `proprietary_codecs=true ffmpeg_branding=Chrome` (patent licensing) and Widevine licensing, which pushes Aeri to a custom CEF build pipeline (same cost as option E).
6. **Passkeys:** apply to Apple for `com.apple.developer.web-browser.public-key-credential` early (organisation Account Holder; approval time unknown); passkey UI should be assumed Chrome-style-only.
7. **Rust bindings:** cef-rs is the viable path (current, tracks stable within days, Apache-2.0/MIT) but has effectively one maintainer; budget for forks/patches or an ObjC++ shim for gaps (signing, GPUI run-loop integration, `CefAppProtocol` on GPUI's `NSApplication`).
8. **Release engineering:** pin `CEF_API_VERSION`, ship the credits/notices, sign helpers inside-out with the JIT entitlement on renderer/GPU helpers, and plan monthly updates (or LTC hops).

## Unknowns that need a spike

Each is a minimal experiment, in priority order.

1. **Layering GPUI over a Chrome-style Views window (options B, C).** Build a tiny C++/Rust app (cef-rs `cefsimple` Views example) with `IsFrameless=true`, `CEF_CTT_NONE`, then from the same process add a transparent borderless `NSWindow` via `addChildWindow:ordered:` (and separately a Metal `NSView` added to `CefWindow::GetWindowHandle()`'s window) with a hole/click-through region. Verify: input routing, live-resize sync, drag/hit-testing, and 60/120 Hz smoothness. Pass/fail: sidebar slides over the page, clicks reach the page in the hole, no flicker on resize.
2. **CWS install end-to-end (completion).** In a Chrome-style Views app, press "Add extension" for uBO Lite and Bitwarden (a human or Accessibility-enabled script); confirm the extension persists across restart under a non-default `root_cache_path/<profile>`; check update/CRX-verification behaviour and the unbranded-build "not from Chrome Web Store" paths. Also check whether install works with a `CEF_CTT_NONE` window.
3. **Extension action popups without a Chrome toolbar.** In the same Chrome-style app with `CEF_CTT_NONE`, call `Extensions.triggerAction` (needs `--remote-debugging-port` + `--enable-unsafe-extension-debugging`) and `CefBrowserHost::ExecuteChromeCommand` for the extensions menu; record whether it crashes (source has no null check) and where the popup anchors. Also repeat with `CEF_CTT_LOCATION`/`NORMAL` clipped to 1 px.
4. **Per-profile cost and isolation.** Create 1, 2, 5, 10 `CefRequestContext`s (`cache_path` = `root/<id>`) each with one page on the same site; record RSS per process type (`CefTaskManager` and `ps`), process counts, startup time per new profile, and verify cookies, `localStorage`, IndexedDB and cache do not cross. Repeat with the same extension (uBO Lite ruleset) loaded in each profile. Also check a closed profile returns memory (dormant cost).
5. **Alloy hide/occlusion throttling and rest.** With an Alloy browser in an NSView, set `NSView.hidden = YES` / order window out and measure renderer CPU, timers (`setInterval` rate) and `document.visibilityState`; compare Chrome-style behavior; test `CloseBrowser` + recreate with state restore time.
6. **Request-intercept latency.** Implement `OnBeforeResourceLoad` that returns `RV_CONTINUE` immediately and one with a Rust matcher; compare page-load time/CPU vs no handler on a 20-page corpus (Chrome-style and Alloy); also test whether `ws://` requests hit the handler (expected: no).
7. **Message-loop integration with GPUI.** Run `external_message_pump=true` with `CefDoMessageLoopWork` driven from the GPUI/AppKit loop; confirm live resize, menu tracking and modal sheets don't stall CEF; verify `CefAppProtocol` on GPUI's `NSApplication` subclass; then test clean shutdown with N profiles (no orphan helpers, no cache-lock files).
8. **Passkeys on an entitled build.** Sign a minimal Chrome-style CEF app with `com.apple.developer.web-browser.public-key-credential` (needs Apple approval; try with a development provisioning profile if possible) and run `https://webauthn.io` registration; separately test Alloy. Record whether the Touch ID path (compile-time team id) works at all.
9. **Codecs/DRM.** Decide if Aeri accepts the gap; if not, time a self-built CEF with `proprietary_codecs=true ffmpeg_branding=Chrome` on Apple Silicon and test Widevine (CDM install path under CEF) on a DRM test page.
10. **Native messaging with real vendors.** Install 1Password/Bitwarden desktop apps; see which `NativeMessagingHosts` directories their installers write (Chrome/Chromium/Edge/…), and whether their host binaries accept a non-allow-listed browser (Aeri's `root_cache_path/NativeMessagingHosts` or `/Library/Application Support/Chromium/NativeMessagingHosts`, both read by unbranded Chromium: Chromium 156 `chrome_paths.cc`/`chrome_paths_mac.mm`).
11. **CDP-based install risk/benefit.** If used for preinstalled extensions: check `Extensions.loadUnpacked` targets the intended profile (it uses the default devtools context), persistence after restart for the CRX/unpacked store you control, and the security cost of leaving a debug port open (prefer `--remote-debugging-pipe`).
12. **cef-rs on Apple Silicon with Views + helper signing.** `bundle-cef-app` a Views example, add inside-out signing and notarisation (JIT entitlement on renderer/GPU helpers) in a script, and test a hardened-runtime, notarised build launches and renders.
