# WebView2 (Windows) as an alternative engine route for Aeri

Research date: **2026-11-18**. Author: WebView2RouteResearch.
Labels: **Observed** = verified in a primary source I read (Microsoft Learn / API reference, maintainer-authored text, source at a named commit, registry API). **Reported** = a third party's statement in a primary tracker (e.g. a user in `MicrosoftEdge/WebView2Feedback`), not confirmed by Microsoft. **Inferred** = my reasoning.
Numbers in `[n]` point to the Sources section. Existing evidence is **not** repeated: CEF facts come from `docs/research/cef.md`, GPUI facts from `docs/research/gpui.md`, blocking/credentials from `docs/research/blocking-and-credentials.md`, codecs/DRM from `docs/research/codecs-drm.md`.

**What I ran.** `curl` of Microsoft Learn pages (markdown rendering) and raw GitHub files; the GitHub REST API (issues/comments of `MicrosoftEdge/WebView2Feedback`, until the 60-requests/hour anonymous limit ran out; the rest via the HTML pages); crates.io API; Chrome's `versionhistory.googleapis.com`; read `/tmp/gpui-fast` (`bf313b4`, 2026-11-17), `/tmp/gpui-component` (`b63a46f`) and `/tmp/wry` / raw `wry@4b2f030`. I unpacked `webview2-com-sys-0.39.1` from crates.io and grepped its bindings. **I did not run WebView2**: there is no Windows machine in this environment, so every statement about runtime behaviour is documentation, source or tracker evidence, never my own measurement. Anything that needs a Windows run is listed under "Unknowns that need a spike".

**Bottom line (Inferred from the findings below).** WebView2 is real Chromium (Edge), so page compatibility, H.264/AAC and PlayReady are good, and maintenance and installer size are far lower than CEF. But for Aeri's top requirement, **Chrome Web Store extensions in the first usable release with popups and actions**, WebView2 has *less* host surface than CEF's Chrome style: no store install (Microsoft refuses by design), unpacked-folder-only `AddBrowserExtension`, no action/popup/side-panel hosting API (open request filed 2026-11-11), and Microsoft calls related work "low priority". It also exists **only on Windows**, so it cannot replace CEF on the Mac-first target; it would add a second engine seam. Recommendation is in "Implications for Aeri".

## Q1. Engine, Evergreen runtime, fixed version, compatibility

**Observed — it is Edge's Chromium.** "The WebView2 Runtime contains modified Microsoft Edge binaries that are fine-tuned and tested for WebView2 apps"; no Start-menu entry or shortcut [1]. "The Runtime generally provides the same web platform capabilities and update release cadence as the Stable channel of the Microsoft Edge browser" [2]. A WebView2 app can only use the Runtime in production, never the installed Edge Stable [2].

**Observed — version currency (today, 2026-11-18).**
- Edge Stable **157.0.4341.42** shipped 2026-11-05; updates through **157.0.4341.60** on 2026-11-13 [5]. Edge 158 is scheduled for "week of 19-November-2026"; since Stable 152 Edge moved to a **2-week major cadence** [4].
- Chrome Stable (win64) is **158.0.8127.37**, serving from 2026-11-17 (`versionhistory` API, queried 2026-11-18) [6].
- For comparison, `cef.md` records CEF stable at Chromium **156** (156.0.30). So today's WebView2 Runtime (157) is one major *behind* Chrome and one major *ahead* of CEF stable. **Inferred:** WebView2 tracks Chrome within about a week or two; it is not a lagging engine. A tracker report on 2026-11-11 used Runtime `157.0.4341.46` [15], consistent with the table.
- **Observed:** Evergreen gives the app no control over the version: "Your app cannot specify that a particular version of the WebView2 Runtime is required" [1]. Apps must feature-detect new APIs (`QueryInterface`), and an event `NewBrowserVersionAvailable` tells the app a newer runtime exists; it is only used after all environment references are released or the app restarts [2][3].

**Observed — fixed-version option.** The app downloads a specific runtime, ships it (**"over 250 MB"**) and points `browserExecutableFolder` at it; it "isn't automatically updated", "can't be installed by using an installer", and on Windows 10 unpackaged apps must run `icacls … /grant *S-1-15-2-2:(OI)(CI)(RX)` (from Fixed 120, AppContainer renderer) [1][2]. The download page keeps only the latest two majors [2]. **Reported:** the Fixed runtime lacks PlayReady that Evergreen has (issue #4632, 2024-06-15, Cider developers; a Microsoft collaborator asked whether Evergreen works, the reporter said yes) [43].

**Compatibility (Observed + Inferred).** The user agent seen in issue #3694 (runtime 117 canary) is `Chrome/117.0.0.0 … Edg/117.0.2024.0` [13]; the host can override `CoreWebView2Settings.UserAgent` [26]. **Inferred:** engine behaviour is Blink at Edge's version with Edge's feature flags, so "sites behave as in Chrome" holds to the same degree it holds for Edge: very high, with residual differences where a site sniffs `Edg/`, or where Google-only services (Chrome sync, Google Pay, the Chrome Web Store) are absent. Microsoft also controls which Chromium features are enabled: `AdditionalBrowserArguments` passes switches to the browser process but "specific features are disabled internally and blocked from being enabled", and an important switch "is ignored" [9b]. Edge's own Chromium *policies* do not apply to WebView2 (see Q10) [47].

## Q2. Extensions

**Observed — the whole official API surface.** Four types: `CoreWebView2EnvironmentOptions.AreBrowserExtensionsEnabled`, `CoreWebView2Profile.AddBrowserExtensionAsync(extensionFolderPath)` / `GetBrowserExtensionsAsync()`, and `CoreWebView2BrowserExtension` with only `Id`, `Name`, `IsEnabled`, `EnableAsync(bool)`, `RemoveAsync()` [8][10][11]. Introduced as Experimental in Prerelease SDK 1.0.1988 (Runtime 117, 2023-07-24), Stable in **Release SDK 1.0.2210.55 (2023-12-11)** [12]; the Win32 interface is `ICoreWebView2EnvironmentOptions6` / `ICoreWebView2Profile7` [9]. The Microsoft spec describes the feature as: install from folder path, list, get id/name, remove, enable/disable [11].
- `AreBrowserExtensionsEnabled` defaults to **false**; when false "new extensions can't be installed, and already installed extension won't be available". Connecting to an already-running environment with a different value fails with `ERROR_INVALID_STATE` [8][9]. It is an *environment* option, so it applies to every profile in the environment.
- `AddBrowserExtensionAsync` **takes an unpacked folder only**: "the extension path for unpacked extensions from the local device… topmost folder… contains the manifest". It "is running right after installation". "During installation, the content of the extension is not copied to the user data folder. Once the extension is installed, **changing the content of the extension will cause the extension to be removed**." The install is persisted per profile; two extensions with the same Id keep only the later one. Errors: `ERROR_NOT_SUPPORTED` (disabled), `ERROR_FILE_NOT_FOUND` (no valid manifest), `E_ACCESSDENIED` (file/dir name starting with `_`), `E_FAIL` [7]. **Inferred:** Aeri would have to keep a read-only, immutable unpacked copy per extension version outside the UDF.

**Observed — no Chrome Web Store / Edge Add-ons install path, by design.**
- Issue #3694 (2023-08-08), Microsoft's `dianaqu` (2023-08-09): "It's by design to not allow extension to be installed through the store." Microsoft's `nishitha-burman` (collaborator, 2023-08-14): "WebView2 does not plan to support installing extensions in WebView2 through Edge/Edge Store. Edge and WebView2 are different entities and an extension being in Edge Store does not mean it is licensed to be used in WebView2. What WebView2 does support is a BYO extension mechanism" [13]. I found no later Microsoft statement reversing this.
- **Reported** workarounds in the same thread: copy an installed extension folder from `%LOCALAPPDATA%\Microsoft\Edge\User Data\Default\Extensions\<id>`, or download the CRX from the Edge store URL and unpack it yourself (a user's C# CRX unpacker is posted there, 2024-03) [13]. Nothing there is endorsed by Microsoft.
- **Inferred:** CWS is technically reachable the same way as in `cef.md` option A: Aeri downloads the CRX (update-URL protocol), verifies the CRX3 signature, unpacks to a folder and calls `AddBrowserExtensionAsync`. That makes Aeri the extension installer, updater and permission-prompt UI; Chromium's own store install flow does not exist here. Whether an unpacked CWS extension keeps its CWS extension id (the id derives from the manifest `key`, else from the folder path; a CRX unpack drops the key unless Aeri re-adds the CRX header's public key) matters for password managers that pin their id in native-messaging `allowed_origins`: **Inferred, unverified**, spike W3.
- A third-party browser built on WebView2 with a Rust host (`webview2-com`) says it installs extensions "only after their signature is verified" — i.e. it built the install path itself (issue #5805, 2026-11-11) [15].

**Observed — which extension APIs work.** There is **no official supported-API table** for WebView2 extensions: the Learn "extensions" concept page I tried returns 404 and the spec lists only the management API [11]. Evidence by feature:
- **Reported (issue #5805, 2026-11-11, runtime 157.0.4341.46, Win32 host):** an MV3 extension "installs and loads successfully; `chrome.sidePanel`, `chrome.tabs`, `chrome.debugger` and other APIs are available to it" [15].
- **`chrome.tabs`:** Microsoft (`sandeepchads`, 2025-03-02, issue #3855): "The WebView2 control creates its own browsing context, which includes its own set of tabs. When an extension calls `chrome.tabs.query`, it queries the tabs within this context, leading to the WebView2 instance being identified as the active tab" [16]. So, unlike CEF Alloy (`tabs.query` → `[]`, `cef.md`), each WebView2 behaves as a tab; but mapping extension tab ids to the host's tabs has no API (issue #3854, open, Microsoft 2024-10-30: "this continues to be **low priority on our backlog**") [16][18].
- **Content scripts, MV3 service workers, declarativeNetRequest, native messaging:** no Microsoft statement found. The Chromium extension system runs inside the runtime, so content scripts and DNR very likely run (**Inferred**; CEF Alloy ran both in the `cef.md` probe). Native messaging: **Unknown** (which registry hive Edge-branded Chromium reads for the host manifest is not public; `blocking-and-credentials.md` only covers Chromium/Chrome branding). Spike W1.
- **Host↔extension communication** has no API: DuckDuckGo (building a WebView2 browser) asked for one (issue #3851, 2023-10-06, open) and today attaches Chrome DevTools sessions via `Target.attachToTarget`, uses `Runtime.bindingCalled` / `Runtime.evaluate` and JS shims for `chrome.tabs.query` etc.; related open requests: code injection before extension code runs (#3852), an API-shim mechanism (#3853), tab-id mapping (#3854), excluding a WebView2 from extension access (#3855) [16]. Their list of APIs needed for a UI-less privacy extension was runtime messaging, tabs (`update`, `sendMessage`, `onCreated/onUpdated/onRemoved`, `query`), `scripting`, `storage` (issue #3258, 2023-07-07) [14].

**Observed — action / popup / side-panel UI: the host must build everything, and there is no API to host it.** Issue #5805 (open, 2026-11-11): "a host app has no way to show an extension's side panel or action popup… The only option is to navigate a `CoreWebView2` to `chrome-extension://<id>/sidepanel.html`. That page runs in a tab context: `sender.tab` is set, `chrome.tabs.getCurrent()` returns a tab, and `chrome.runtime.getContexts()` reports TAB, not SIDE_PANEL. Extensions that verify they are running in a real side panel… refuse to run." The reporter asks for APIs to host the side panel/popup as a genuine context and fire `chrome.action.onClicked` [15]. Microsoft has not answered there (0 comments as of my read). Other open gaps: icon/popup/options page URL are not exposed (`ICoreWebView2BrowserExtension` has only id/name/enabled; issues #3856 (2023-10-06) and #5084 (2025-02-04), a Microsoft reply asked "what scenario would this light up") [16][17]; no way to turn on the extensions developer mode (#5088, listed in #5084). The initial API was described as "UI-less" by the party that filed #3258 and Microsoft has not said otherwise [14]. **Inferred:** Aeri would parse `manifest.json` itself for icons/`action.default_popup`/`options_ui`, host popups in extra WebView2s on the same profile (tab-context caveat above), and implement `chrome.action` click routing through CDP shims. That is the same job as `cef.md` option A, with a thinner API.

**Observed — Rust host reference.** `wry@4b2f030` (`src/webview2/mod.rs:367-368, 653-660, 1525-1540`): sets `AreBrowserExtensionsEnabled` from a builder flag and, when an `extension_path` is given, calls `ICoreWebView2Profile7::AddBrowserExtension` for each subfolder [46]. Nothing about popups.

## Q3. Profiles and user data folders

- **Observed — model.** One `CoreWebView2Environment` = one user data folder (UDF) = one browser process plus its renderer/GPU/utility children [20]. "Multiple profiles under a single user data folder": each profile "has a dedicated profile folder" under the UDF, and "all WebView2 controls associated with the same user profile share a single profile folder" [19]. Profile is chosen per controller via `CoreWebView2ControllerOptions.ProfileName` (+ `IsInPrivateModeEnabled`) with `CreateCoreWebView2ControllerWithOptions` / `…CompositionControllerWithOptions` (Win32 `ICoreWebView2Environment10`, SDK 1.0.1210.39) [19][22]. A profile that does not exist is created on first use [19].
- **Observed — cost model.** Microsoft's own motivation: the older pattern of one UDF per control meant "multiple WebView2 runtime instances (each including a browser process and a bunch of child processes), which consumed more system resources including memory, CPU footprint, and disk space" [19]. So extra profiles under one UDF share **one browser process**. Microsoft gives **no per-profile number**. **Inferred (Chromium's design):** renderers are not shared between profiles (a site instance belongs to one browser context), so each *active* profile adds its own renderers, while GPU/network/utility processes are shared; a dormant profile with no controller costs disk only. Service workers are per profile: `WebResourceRequested` for service/shared workers "is not raised for requests… that belong to a different `CoreWebView2Profile`, including an InPrivate profile, even if both profiles share the same `CoreWebView2Environment`" [24] (isolation evidence). Per-profile settings: cookie manager, password/autofill toggles, `ClearBrowsingData`, tracking-prevention level, permission state, extensions (installed and `IsEnabled` persisted per profile) [10][21][41].
- **Observed — rules and limits.**
  - Profile name: ASCII `a-z A-Z 0-9 # @ $ ( ) + - _ ~ . space`, **max 64 characters**, case-insensitive (it maps to a directory), must not end with `.` or space; invalid → `E_INVALIDARG` [22].
  - All profiles in an environment share the environment options: creating a second environment on the same UDF with different options (e.g. different `Language`) fails to create WebView2s, in-process or cross-process; identically-configured environments attach to the same process group [20]. `AreBrowserExtensionsEnabled` mismatch → `ERROR_INVALID_STATE` [8].
  - UDF must be writable, not on a network drive ("slowdowns, crashes, or loss of data"); the default UDF sits next to the `.exe` and fails under protected install dirs, so unpackaged apps should pass a custom path (Aeri's `%LOCALAPPDATA%\Aeri\` fits); a UDF "may only be shared among host apps in the same logon session" [21].
  - **Deletion is deferred:** `Profile.Delete()` "marks for deletion"; the directory "will be deleted at browser process exit"; if files are held it retries "at all future browser process starts"; re-creating the same name meanwhile fails with `ERROR_DELETE_PENDING`; the profile's WebView2s are closed and a `Deleted` event fires [23]. **Inferred:** Aeri's "delete profile removes all its data, including saved sign-ins" needs an explicit pre-delete `ClearBrowsingData(AllProfile)` (documented to clear data but **not** account-scoped data such as passwords [21]) and a pending-delete state in the UI; with CEF, Aeri controls the directory directly.
- **Unknown:** the practical ceiling on simultaneously open profiles; memory per extra active profile; whether `Environment.GetProcessExtendedInfos` can attribute renderers to profiles. Spike W5.

## Q4. Content blocking: `WebResourceRequested`

**Observed — scope.**
- A filter is a URI glob (`*`, `?`) plus a resource context (`ALL, DOCUMENT, STYLESHEET, IMAGE, MEDIA, FONT, SCRIPT, XML_HTTP_REQUEST, FETCH, TEXT_TRACK, EVENT_SOURCE, **WEBSOCKET**, MANIFEST, SIGNED_EXCHANGE`) [26]. At least one filter is required for the event to fire; default schemes are `file`, `http`, `https` and registered custom schemes [25].
- The classic `AddWebResourceRequestedFilter` is **deprecated**: it "will cause the event to fire only for the main frame and its same-origin iframes". `AddWebResourceRequestedFilterWithRequestSourceKinds` (`ICoreWebView2_22`, **SDK 1.0.2365.46**) adds `DOCUMENT` (page incl. dedicated workers, iframes, main script of shared workers), `SHARED_WORKER`, `SERVICE_WORKER`, `ALL`. Filters "have to be added before main page navigation". Worker events fire for *any* WebView2 in the same profile with matching filters, so Microsoft says to register worker filters on **one WebView2 per profile** to avoid duplicates [24].
- The request "may be missing some headers that are added by network stack at a later time" [25]; the event has no frame/site origin (open request #3525, 2023-05-31, "Add Site Origin and Frame Origin to WebResourceRequested") [28].

**Observed — threading and cost.** WebView2 is an STA/COM object; "all callbacks occur on that thread… It isn't safe to use the WebView2 from another thread"; the only exception is the request `Content` stream [27]. The event is **synchronous with the network request**: "The web resource requested may be blocked until the event handler returns if a deferral is not taken… blocked until the deferral is completed" [25]. A handler can set a `Response` to complete the request itself (so blocking = returning an empty/403 response) [25]. Microsoft publishes **no performance figure** for this path. **Inferred:** every matching request costs a browser-process → host-process hop onto the UI thread, so a catch-all `*` filter puts adblock-rust matching (~µs per request) behind every subresource on the same thread that renders GPUI and forwards input; the deferral path lets matching run on a worker thread, but completion still returns to the UI thread. Needs measurement (spike W4).

**Observed — known holes relevant to a blocker (open issues, Reported by users, none answered by Microsoft in the threads I read).**
- #5765 (2026-10-17): no events for subresources of a **nested cross-origin iframe**, though its navigation fires, "even with a catch-all filter and `SourceKinds.All`"; cites older #5376 and #4447 [28].
- #5787 (2026-10-29): same for cross-origin iframe subresources in a WebView2 created via `NewWindowRequested` (popups), still unfixed after the #4689 workaround (re-adding filters after `NewWindow` is set) [28].
- #5764 (2026-10-16, runtime 155): when a WebView has *any* filter (even one matching nothing), a service worker using static routing (`addRoutes`, e.g. Gmail's `sw.js`) often sticks in `STARTING`; reproduced 6 of 7 runs with a non-matching filter vs 0 of 7 without; Gmail then loads without icons and never finishes loading [28]. For an always-on blocker this is a direct site-compatibility regression.
- **WebSockets:** the enum has a `WEBSOCKET` context, but I found no doc saying whether a response can be substituted or the handshake blocked for it. **Unknown**, spike W4.

**Observed — no DNR-like built-in.** Search of the API list [26][33] and release notes finds no declarative blocking API; WebView2 offers `WebResourceRequested`, `NavigationStarting`/`FrameNavigationStarting`, `AddScriptToExecuteOnDocumentCreated`, and raw CDP (`CallDevToolsProtocolMethod`). **Inferred options:**
1. *adblock-rust in the handler* (see `blocking-and-credentials.md` for the crate). Per-request input is the URL, headers and context; `$third-party`/`$domain` options need the *source* URL, which the event does not carry (#3525), so Aeri must track the document/frame URL itself from navigation and `CoreWebView2Frame` events. Cosmetic filters use `AddScriptToExecuteOnDocumentCreated` (exists, per-WebView2) [26]. Works, but inherits all holes above.
2. *uBO Lite via the extension path*: DNR runs inside Chromium, avoiding the per-request IPC and the iframe/SW holes (**Inferred**, only if the extension actually loads: spike W1).
3. *CDP `Fetch.enable`/`Fetch.requestPaused`* as a second interception layer (**Inferred** from the CDP surface, untested here).

## Q5. Performance and resource control

**Observed — suspend / memory APIs.**
- `ICoreWebView2_3::TrySuspend` / `Resume` / `IsSuspended` (**SDK 1.0.774.44**): "similar to putting a tab to sleep in the Edge browser"; pauses timers/animations, "minimizes CPU usage for the associated renderer", lets the OS reuse the memory. Requires the controller's `IsVisible == false` (else `ERROR_INVALID_STATE`); best effort (the completed handler gets `isSuccessful=false` if sleeping-tab conditions fail; a running script finishes first); auto-resumes when visible [29].
- `ICoreWebView2_19::MemoryUsageTargetLevel` `Low|Normal` (**SDK 1.0.1823.32**): scripts keep running and connections stay alive; Low may swap some browser-process memory to disk; "best effort"; does not revert automatically; **do not mix with `TrySuspend`** [30]. Microsoft's performance page recommends Low for inactive WebViews and `TrySuspendAsync` for ones unused "for a while" [33].
- **IsVisible = false** is the precondition for suspend; it is the way to tell Chromium a tab is hidden (the doc ties Edge's sleeping-tabs conditions to it) [29].
- **No discard API.** **Inferred:** a "discarded" tab = close the controller (`Close()` shuts down the WebView and its renderer per [20]) and keep Aeri's own session state; re-open later with a new controller on the same profile. Restoring scroll/form state is Aeri's job.

**Observed — process and resource reporting.** `Environment.GetProcessExtendedInfos` (**SDK 1.0.2210.55**) returns a snapshot of all processes of the environment (excluding crashpad); each entry has only `Kind` and `ProcessId` plus, for renderers, `AssociatedFrameInfos` (frames "actively running (showing or hiding UI elements)") [31][32]. `OpenTaskManagerWindow` shows the Edge browser task manager [20]. **No memory/CPU numbers** are in the API; **Inferred:** Aeri reads them from Windows (`GetProcessMemoryInfo`/PDH) per pid. Per-tab attribution is approximate because "a given renderer process is not associated with a single `CoreWebView2` instance… the renderer process can serve frames in multiple `CoreWebView2` instances that use the same user data folder" (site isolation/process sharing) [20]. CEF's Chrome-style Task Manager data path is in `cef.md`.

**Observed — process model.** All processes of a group hang off **one browser process per UDF** ("a single, specific browser process in a WebView2 process group"), created when the first WebView2 for that UDF starts; its lifetime governs the rest [20]. Microsoft's performance page is looser ("each WebView2 control creates its own set of processes, such as browser, renderer, and GPU") but its fix is "use one `CoreWebView2Environment` across all WebView2 controls… tabbed interfaces" [33]; the process-model page is the more specific source. The browser process of a shared UDF may be shared even across different apps with identical options ("app-level process sharing") [33], and a new "Shared Cluster Environment" API for cooperating apps is experimental in Prerelease SDK 1.0.4255 (2026-09-11) [12b].
**Observed — footprint benefit:** "On eligible systems, binaries for Microsoft Edge and the Evergreen WebView2 Runtime are hard-linked together when they are on the same version… benefits for disk footprint, memory, and performance", and if Edge is running at the same version "the required WebView2 binaries are already in memory" [2][33]. **Inferred:** on a machine where Edge is open, Aeri on WebView2 can be lighter than a self-contained Chromium; "lighter than Helium" is plausible but **unmeasured** (spike W5).

## Q6. UI integration with GPUI on Windows

**Observed — what GPUI does on Windows** (from `gpui.md`, zed@9636213): D3D11 + DirectComposition flip-model swap chain, premultiplied alpha, `WS_EX_NOREDIRECTIONBITMAP`; `RawWindowHandle::Win32(hwnd)` of the top-level window is available; no GPU-surface primitive on Windows (`draw_surfaces` is a no-op) [40]. Zed PR #66368 ("Keep child windows above GPUI content", merged 2026-11-02) changed `CreateTargetForHwnd(hwnd, topmost)` to `false` so child HWNDs stay above GPUI's content [38][40].

**Windowed hosting.** WebView2 is a child HWND of the GPUI window, as `wry` does (`WS_CHILD | WS_CLIPCHILDREN`) and as `gpui-webview` does. **Observed:** it covers GPUI drawing in its bounds, including popovers/menus/tooltips: `gpui-webview` README (gpui-component@b63a46f) "Windows | WebView2 | **Not yet; the WebView covers overlays**… use the webview in a separate window or a Popup layer when overlapping GPUI content is required" [39]. Windowed hosting handles input, focus/tab traversal, DPI-scaled child windows and accessibility via the OS [34]. This matches the existing Aeri assumption for CEF on Windows (`02-tech-stack.md`).

**Visual hosting (composition).** **Observed (Microsoft):** `CreateCoreWebView2CompositionController` returns an object with the same API as the normal controller plus `RootVisualTarget` (an `IDCompositionVisual`, `IDCompositionTarget` or `Windows.UI.Composition.Visual`; **not** WinAppSDK `Microsoft.UI.Composition`), `SendMouseInput`, `SendPointerInput` (touch/pen), `CursorChanged`/`Cursor`/`SystemCursorId`, and `AutomationProvider` (UIA) [34][35][36]. The host "takes spatial input… and sends this input to the WebView2", scales with `RasterizationScale`, and routes input itself; drag and drop and accessibility are separate host duties [34]. SDK 1.0.774.44 [35]. "Window to Visual" mode (`COREWEBVIEW2_FORCED_HOSTING_MODE`) still renders into an HWND [34], so by itself it does not escape the child-window overlay problem (**Inferred**).

**Could GPUI's DirectComposition tree host the WebView2 visual? Yes in principle; stock GPUI does not expose it; one fork does.**
- **Observed — stock GPUI:** no API to obtain the window's `IDCompositionDevice`/visual or to reorder surfaces; the in-tree composition PR **zed#62379** "gpui: Add native window composition support" is still **open** (created 2026-08-09, updated 2026-11-18) [38].
- **Observed — gpui-fast README claim.** `gpui-fast` README "Window composition": "Opt-in composition supports macOS, Windows and Linux… GPUI menus, popovers and dialogs… render above the native content on all three"; table row "Windows | WebView2 composition | Overlay layer" [37]. The **same ecosystem is inconsistent**: `gpui-webview` (gpui-component@b63a46f) says Windows "Not yet" [39].
- **Observed — what the code actually does** (gpui-fast@bf313b4, 2026-11-17): `crates/gpui_windows/src/fast/composition.rs` replaces the target root with its own visual that holds, in order, GPUI's base swap-chain visual, native-surface visuals, and one visual per GPUI overlay surface (each with its own swap chain, presented together); a native surface is a visual with a rectangle clip, positioned at its bounds and hidden through opacity; `platform_handle()` returns that visual as `IUnknown`; device-loss `recreate` rebuilds the tree and calls each surface's `compositor_recreated` callback [37]. `crates/gpui_perf/examples/native_webview.rs` (Windows branch, uses `webview2-com 0.39`) creates the environment, calls `CreateCoreWebView2CompositionController(hwnd)`, `SetRootVisualTarget(visual)`, `SetIsVisible(true)`, `NavigateToString`, forwards mouse move/buttons/wheel/horizontal-wheel through `SendMouseInput`, updates bounds on layout, and `SetFocus(gpui_hwnd)` to hand keyboard focus back to GPUI [37].
- **Assessment (Inferred):** rendering order and mouse routing are demonstrated *in code*; I did not run it (no Windows). In that example I found **no** use of `SendPointerInput` (touch/pen), `CursorChanged` (the page cannot change the cursor, e.g. I-beam), drag-and-drop, UIA `AutomationProvider`, IME composition forwarding, or DPI/`RasterizationScale` handling for nested scale; and only a static `NavigateToString` page was shown, not a real site. All of those are things a browser needs, and `gpui-fast` is a third-party fork of Zed pinned to `zed_commit 78f5d74…` (UPSTREAM file) that depends on an unmerged PR [37][38]. So the README claim is **supported at the level of a rendering demo, unproven at browser level**.
- **Alternative that avoids the fork (Inferred, untested):** keep WebView2 in a child HWND and put Aeri chrome that must float over the page in separate top-level transparent GPUI windows (as proposed for macOS in `gpui.md` Q4); z-order, focus and activation are the spike items.

## Q7. Media: H.264/AAC, Widevine, PlayReady

- **H.264/AAC.** **Reported:** a commercial user states the WebView2 redistributables include the H.264 codec and asks for an installer without it for licensing reasons (issue #4329, 2024-01-29, open, assigned to Microsoft since 2025-02-12): "Distribution of H264 gives issues… we would rather get rid of it" [44]. **Inferred:** Edge's runtime ships proprietary codecs (H.264/AAC/MP3) in the Evergreen runtime; because Microsoft, not Aeri, distributes and licenses it, Aeri avoids the self-build + patent-licence problem in `codecs-drm.md`. Platform HEVC depends on the OS (issue #4285, 2024-01-10: HEVC blank screen on some Windows SKUs) — **Reported**, not an Aeri requirement.
- **PlayReady.** **Reported (production evidence):** the French streaming app myCANAL ships on WebView2 (UWP) with `playready.software/hardware/recommendation` key systems; black-screen bug with SL3000 on Windows 11 24H2, closed 2024-11-19 (issue #4935) [43]. The Cider developers say PlayReady works in Evergreen but not in the Fixed runtime (#4632) [43].
- **Widevine.** **Unknown / weakly Reported.** A 2021 report used DirecTV (Widevine) in a Fixed 94 runtime, "inconsistent" failures (#2021) [43]; a 2024-09-21 feature request says "Webview2 support playready already and enabling widevine support will be more helpful" and Microsoft only asked for the reporter's workaround (#4828, open) [43]. I found no Microsoft statement on Widevine in WebView2. **Inferred:** do not assume Widevine L3 works in WebView2.
- **Netflix and Spotify.** I found **no primary source** (Microsoft docs, Netflix/Spotify statements, or a tracker thread) showing either service playing inside a third-party WebView2 app; I will not guess. The Spotify Community thread I found is about CEF in Unity. Spike W7 (`requestMediaKeySystemAccess` for `com.widevine.alpha` / `com.microsoft.playready*`, then log in to both).
- For comparison, `codecs-drm.md`: stock CEF has no H.264/AAC and no VMP signing; production DRM on macOS/Windows via CEF is not available without castLabs-style signing. On this requirement WebView2 on Windows is clearly ahead for PlayReady and H.264/AAC, undetermined for Widevine.

## Q8. Passwords and passkeys

- **Observed — API.** `CoreWebView2Settings.IsPasswordAutosaveEnabled` (**default `FALSE`**) and `IsGeneralAutofillEnabled` (default `TRUE`; excludes passwords and cards), mirrored on `CoreWebView2Profile` (SDK 1.0.902.49 / `ICoreWebView2Profile6`); they are per profile. When password autosave is true, "password information is auto-populated, suggestions are shown… new data is saved, and a Save/Update Password prompt is displayed"; when false, no new data is saved but previously saved data still autofills [41]. `ClearBrowsingData` has `PASSWORD_AUTOSAVE` and `GENERAL_AUTOFILL` kinds [21][26].
- **Observed — absences.** In the API list I read [26][33] there is **no API to enumerate, export, import or edit saved passwords**, to supply a credential provider, or to sync them. **Inferred:** WebView2 offers Edge's local per-profile autofill and nothing else; Aeri's "basic password store" (`keyring-core`, blueprint) would have to be fed by Aeri's own form handling via script injection or a password-manager extension (which brings back Q2). The built-in store is local to the UDF; `AllProfile` clearing "doesn't delete account-scoped data, such as passwords" [21].
- **Passkeys / Windows Hello.** **Reported (all open, none answered with a Microsoft design statement):** WebAuthn reaches the Windows security prompt from WebView2 — "Windows security key prompt" on ebay.com's "sign in with Windows Hello" (#5292, 2025-07-02), unwanted passkey enumeration prompt on Google sign-in with no host switch (#5460, 2025-12-10, still blocking UI tests in 2026-04), plus failures: "WebAuthn / Passkey (Windows Hello) not working in WebView2 while working in Edge and Chrome" (#5663, 2026-08-04) and a Windows Hello window error when clicking a passkey suggestion (#5740, 2026-10-01) [42]. **Inferred:** the Chromium WebAuthn → Windows WebAuthn API path exists, but UI hooks (suggestions, enumeration) are not host-controllable and the failure rate is unknown; compare `cef.md`: WebAuthn dialogs need Chrome style, "should work with the Chrome runtime" (CEF #3508, #3275, 2022–2023). Neither route is verified on Windows. Spike W8.
- **Password-manager extensions** (Bitwarden, 1Password) depend on Q2: popup UI host work, id pinning, native messaging to the desktop app (unknown host-manifest location for WebView2), and no `chrome.action` routing.

## Implications for Aeri

1. **Do not replace CEF with WebView2.** It cannot serve macOS, and on Windows it fails or only partly meets the three requirements that define Aeri (CWS extensions with UI; uBO-quality blocking; GPUI over the page). **Inferred** from Q2, Q4, Q6.
2. **If Windows is later built on WebView2 anyway**, treat the extension story as a product, not a feature: Aeri owns CRX download/verify/unpack (immutable folders), id/`key` handling, popup and side-panel hosting in extra WebView2s with the tab-context caveat, `chrome.action` routing and tab-id mapping through CDP shims (what DuckDuckGo describes in #3851–#3855), and native-messaging registration. That is `cef.md` option A with a thinner host API, plus Microsoft's open statement that CWS-style store install is not planned and tab-id mapping is low priority [13][18].
3. **Triggers to revisit** (watch, do not wait): Microsoft answering #5805 with side-panel/popup context hosting; an `AddBrowserExtension` for packed CRX or a store flow; an API for tab/window mapping; a fix for #5765/#5787/#5764. Check these before the Windows phase starts.
4. **Keep the engine seam narrow.** `aeri-core`'s command set (create/close, navigate, profile, blocking, discard) maps cleanly onto both CEF and WebView2 (`CreateCoreWebView2ControllerWithOptions`, `Profile.Delete`, `TrySuspend`, `WebResourceRequested`), so a Windows-only WebView2 experiment is cheap to attempt behind it; but profile deletion semantics (deferred) and blocking semantics (UI-thread callback, holes) differ and should not leak into core.
5. **Windows UI layering stays child-window-beside-page** for CEF or WebView2 unless zed#62379 lands or Aeri adopts gpui-fast; its Windows composition path should be evaluated as a spike, not relied on (Q6).
6. **Codecs/DRM:** WebView2 sidesteps the CEF codec-licensing and VMP problems on Windows (Q7). If Windows media quality becomes decisive, this is the strongest argument for WebView2 on Windows, but Widevine remains unverified.
7. **Owner's question ("native performance and lower engine maintenance")**: for Windows, WebView2 does win on maintenance and installer size (Q10); it does not give a native-UI or native-extension advantage, because the extension and UI host layers are Aeri's either way.
