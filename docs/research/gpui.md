## Q3. Native-handle access

**Observed.** `Window` implements `raw_window_handle::{HasWindowHandle, HasDisplayHandle}` (`crates/gpui/src/window.rs:8056-8068`, zed@9636213; `PlatformWindow: HasWindowHandle + HasDisplayHandle`, `platform.rs:1283`). The `&mut Window` passed to view/`open_window` closures can therefore be handed to any `raw-window-handle` 0.6 consumer (wry does exactly this, below).

- **macOS:** returns `RawWindowHandle::AppKit(AppKitWindowHandle::new(native_view))` — i.e. the **GPUI content `NSView` (class `GPUIView`), not the `NSWindow`** (`gpui_macos/src/window.rs:2566-2576`). `NSWindow` = `-[NSView window]` via objc2 (`gpui_macos` itself does this). `AppKitWindowHandle` has only `ns_view`. The view tree is `NSWindow → contentView → GPUIView(layer-backed CAMetalLayer, autoresize w/h)`; GPUIView is added as a *subview* of the window's content view (`window.rs:1154-1274`, `addSubview: native_view`), with `makeFirstResponder: native_view` right after (`:1274`).
- **Windows:** `RawWindowHandle::Win32(Win32WindowHandle::new(hwnd))` — the top-level HWND (`gpui_windows/src/window.rs:597-605`). `DisplayHandle::windows()`.
- `Window::window_handle()` (GPUI's own `AnyWindowHandle`) is a different, unrelated thing; don't confuse it.
- There is no API to *replace* GPUI's view or to supply your own `NSWindow`/HWND (**Observed**: `open_window` creates both internally; no "attach to existing" option in `WindowOptions`, `platform.rs:2643-2752`). `Inferred`: anything beyond the handle (e.g. subclassing) needs ObjC-runtime tricks, as gpui-cef already does for `NSApplication` (Q6).

## Q4. Hosting a foreign native child view; z-order

**Observed — what happens with stock GPUI.** Any native view parented to GPUI's handle is a sibling/child of `GPUIView` inside the window content view, and AppKit draws subviews above their parent's layer content. **GPUI draws everything into one Metal layer on `GPUIView`; a native child therefore always covers GPUI content in its bounds** — popovers, dialogs, menus, tooltips, and slide-in panels included. Sources:
- gpui-webview README (gpui-component@b63a46f `crates/webview/README.md`): "On gpui-pre, the native view is attached to the window directly. It covers GPUI content in its bounds, including popovers, dialogs, menus and tooltips. It cannot be clipped either…". Windows row: "Not yet; the WebView covers overlays".
- zed#62379 body: "If a WebView is placed above GPUI's renderer, it also covers every GPUI overlay in the same area."

**Observed — how the existing integrations parent/size/clip them (wry path).** `gpui-webview` `WebView::build` calls `builder.build_as_child(&*window)` on the GPUI `Window` (gpui-component@b63a46f `crates/webview/src/lib.rs:~167`). wry reads `RawWindowHandle::AppKit` and does `ns_view.addSubview(&webview)` (wry@4b2f030 `src/wkwebview/mod.rs:210-234, 724/767`); on Windows it reads `Win32`, creates a `WS_CHILD | WS_CLIPCHILDREN` HWND with the GPUI HWND as parent (`src/webview2/mod.rs:108, 264, 291, 301`). Layout sync: a custom `Element` (`WebViewElement`) in `prepaint` reads its laid-out `bounds`, intersects with `window.content_mask()`, and calls `wry::WebView::set_bounds` with window-relative logical coordinates; hides the native view when the clip is empty; inserts a `HitboxBehavior::BlockMouse` hitbox so GPUI content beneath doesn't receive mouse; a `MouseDownEvent` listener outside bounds calls `focus_parent()` to take focus back (`lib.rs` `WebViewElement::{prepaint,paint}`). Partial clipping (scrolled container) is **not possible** without composition: the view keeps full bounds. Resize: the child is positioned every prepaint (every frame the element is repainted) — there is no OS-level constraint/autoresizing link.
- **Reported (third party, one app):** Cydonia hosts WKWebView/WebView2 over GPUI and works around "GPUI paints under it" by **snapshotting the page, moving the real view off-screen (−20,000 pt, because a hidden WKWebView still accepts drops) and painting the still where an overlay appears** (`https://cydonia.sh/blog/a-browser-inside-a-gpui-app/`, 2026-09-28). That is a workaround, not a supported mechanism, and a CEF windowed view can't be snapshot cheaply — **Inferred**.

**Observed — three ways projects get UI "over" the page:**
1. **Off-screen render the page into a GPUI element (no native child).** `bokuweb/gpui-cef` (Apache-2.0/MIT, 47 commits, created 2026-08-25): on **macOS = CEF 151 OSR**, frames drawn as an ordinary GPUI element (so clipping, rounded corners and overlays work; the demo draws a GPUI badge over the page); on **Windows = WebView2 via wry as a native child window ("always in front of gpui's own drawing")** (`gpui-cef@6b6a1d0 README.md`). Runtime: `settings.windowless_rendering_enabled=1`, `external_message_pump=1`, `multi_threaded_message_loop=0` (`platform/cef/mod.rs:96-112`). Costs: see Q5/Q6/Q7. This is the **only existing GPUI+CEF project I found**; `longbridge/wef` (CEF OSR for GPUI) carries a README warning that it is experimental "not good enough… app size (included a CEF Framework increase 1GB), development experience" and Longbridge ships wry instead (`https://github.com/longbridge/wef`, `README.md`, last commit 2025-10-16) — **Observed README text, Reported conclusions**.
2. **Native window composition fork.** `gpui-fast` (third-party fork; opt-in `Window::enable_window_composition()`, ported from open PR zed#62379) splits presentation into ordered surfaces: *GPUI base → native surface → GPUI overlay* (`gpui-fast@bf313b4 crates/gpui/src/fast/composition.rs:1-37`); macOS = AppKit subviews/CAMetalLayers, Windows = DirectComposition visual tree (+ WebView2 composition), Linux = subsurfaces/child windows. gpui-webview with `gpui-fast` on macOS reparents wry's `WKWebView` into a composition surface's `NSView` (`gpui-component@b63a46f crates/webview/src/composition.rs`), giving "GPUI overlays render above the page" on macOS and Linux/X11; README table says **Windows: Not yet** for gpui-webview, though gpui-fast's own README claims Windows WebView2 composition (`gpui-fast README`). **Upstream status: zed#62379 is OPEN** (opened 2026-08-09, updated 2026-11-08). Comments: a user on macOS reports it works but lists issues (every geometry change re-parents all composition views; overlay view takes pointer input for the whole window while it has any content; dropping a surface doesn't remove it; container not click-transparent); on 2026-11-06 a commenter (Anthony-Eid; Zed staff status **not verified**) said "I don't necessarily think this is the right architecture… we should block this until we have a stronger retain mode story… it would refresh the whole window if a native view changed". The smaller alternative zed#61945 ("Render deferred overlays above native child views") is **closed, not merged** (2026-09-27). **Net: no supported upstream mechanism; the composition feature depends on a fork or an unmerged PR.**
3. **Keep native UI beside/around the page**, never over it (works with stock GPUI).

**Not found in any source:** a GPUI project that parents a **CEF windowed** (`CefWindowInfo::SetAsChild`) browser into a GPUI window. **Inferred:** mechanically identical to the wry path (CEF's `SetAsChild(NSView*)` takes a parent NSView; GPUI gives one via `HasWindowHandle`), so it would inherit the same "covers GPUI" limitation; on Windows the CEF child HWND would likewise be above GPUI after zed#66368. gpui-cef's choice of OSR (not windowed) for macOS supports that the author considered the windowed route inadequate for overlays (README "Why Chromium on macOS"). Whether CEF windowed on macOS forces Alloy style and thus blocks extension UI is CefResearch's question; the bezier note says it does — **Reported**.

**Can GPUI draw on top of a native child?**
- Stock GPUI (zed@9636213): **No** — only beside it/outside its bounds. **Observed** (READMEs/PR above; no composition API in `crates/gpui`: `grep WindowCompositionSurface|enable_window_composition` returns nothing in zed@9636213).
- With `gpui-fast` composition: **Yes** on macOS (and per its README Windows/Linux) — fork, experimental.
- With OSR (gpui-cef): **Yes**, because the page is a GPUI texture.
- **Inferred, unproven for GPUI:** put the sliding UI in a *second* GPUI window of `WindowKind::Floating`/`PopUp` (NSPanel; `gpui_macos/src/window.rs:1086-1100, 1280-1310`) with a transparent background (`WindowBackgroundAppearance::Transparent`) stacked over the main window. Caveats: `Floating` uses `NSFloatingWindowLevel` (global float, not a true child window — no `addChildWindow` call exists; grep), `PopUp` is non-activating, `AnchoredPopup` is **rejected on macOS** (`gpui_macos/src/platform.rs:757`). Z-order, focus and Spaces/fullscreen behaviour would all need a spike.
- **Observed, relevant to hit-testing:** a native child keeps its own AppKit hit-testing; GPUI only learns about it by inserting its own `BlockMouse` hitbox (above). Atrium's reported pain (hit-testing) in the bezier note concerns Tauri/AppKit, not GPUI — **Reported**.

## Q5. Off-screen texture path (external GPU surface / pixel buffer)

**Observed — `surface()` element, macOS/iOS only, NV12 only.**
- `crates/gpui/src/elements/surface.rs`: `SurfaceSource::Surface(CFRetained<CVPixelBuffer>)` exists only under `cfg(any(target_os="macos", target_os="ios"))`; `Window::paint_surface(bounds, CVPixelBuffer)` (`window.rs:5595-5612`).
- `gpui_apple/src/metal_renderer.rs:1206-1260`: `draw_surfaces` **requires `kCVPixelFormatType_420YpCbCr8BiPlanarFullRange`** (`anyhow::ensure!`, else error "unsupported surface pixel format"), builds two Metal textures per frame through a `CVMetalTextureCache` (R8 + RG8 planes), and draws them through a YUV→RGB shader. That makes the path **zero-copy for NV12 video** (CVPixelBuffer ↔ IOSurface-backed → Metal texture; the Metal texture aliases the buffer) but it **cannot display a BGRA IOSurface** as CEF's accelerated paint produces. (gpui-cef documents the same: "`surface()` hard-codes NV12… trips an `assert_eq!`" — `gpui-cef@6b6a1d0 options.rs:35-49`; the zed@9636213 code now returns an error rather than asserting.)
- **Windows: no equivalent.** `PaintSurface` has no non-Apple field (`scene.rs:1046-1052`); `directx_renderer.rs:843-848` `draw_surfaces` returns `Ok(())` immediately when non-empty (no-op); wgpu renderer: `PrimitiveBatch::Surfaces(_) => {}` with the comment "Surfaces are macOS-only for video playback and are not implemented by the WGPU renderer" (`wgpu_renderer.rs:1543-1545`). **A GPU-resident external frame on Windows has no GPUI API.**
- **CPU image path (all platforms):** `img()` / `Window::paint_image` with `Arc<RenderImage>` (`RenderImage` is "a cached and processed image, in BGRA format", `assets.rs:42-49`). `paint_image` calls `sprite_atlas.get_or_insert_with(RenderImageParams{image_id, frame_index}, …)` — i.e. each distinct `RenderImage` is **uploaded to the atlas (a CPU→GPU copy)** and remains until `Window::drop_image` / `cx.drop_image` (`window.rs:5493-5545, 5615-5625`). A new `RenderImage::new` allocates a new `ImageId` (`assets.rs:62-69`), so per-frame buffers need explicit drop to avoid atlas growth (gpui-cef does this: `pump.rs` `tick_view`, `cx.drop_image(frame, None)`).
- **Cost model (Observed + Reported):**
  - Per frame via `img()`: CEF `OnPaint` BGRA buffer → `to_vec()` copy (CPU) → atlas upload (CPU→GPU) → draw. gpui-cef measured ("Measured… at 994x786 in a debug build"): **1.2% CPU idle, ~38% CPU across all processes while the page repaints continuously at 60 fps**; "roughly 3.9MB per frame at 1200x820" (`gpui-cef README`, section "How frames get across…") — **Observed text, author-measured; debug build, not independently reproduced**. At Retina full-window sizes the copy scales with pixel count (3024×1964×4 B ≈ 23.8 MB/frame, **Inferred arithmetic**).
  - Zero-copy needs a GPUI patch: a BGRA branch in `paint_surface` + `draw_surfaces` (gpui-cef says CEF→IOSurface→CVPixelBuffer is "verified working" up to GPUI; `accelerated: true` is off by default for that reason). **No such branch exists in zed@9636213** (checked `draw_surfaces`). Windows would need a new D3D11 shared-texture primitive (D3D11 devices in GPUI are created in `directx_devices.rs`; sharing with CEF's D3D11 texture `OnAcceleratedPaint` — **Inferred**, nobody has done it).
- **Observed (CEF side, for completeness, from the brief's secondary source):** OSR forces Alloy style, no smooth scrolling in OSR (CEF #3842 not_planned), external-begin-frame broken on macOS (CEF #4033 open) — **Reported**; belongs to CefResearch.

## Q6. Run-loop integration

**Observed — GPUI owns `[NSApp run]`.** `MacPlatform::run` creates `GPUIApplication` (NSApplication subclass, `gpui_macos/src/platform.rs:70`), sets the delegate and calls `[app run]` inside an autorelease pool (`platform.rs:530-570`). Headless mode uses `CFRunLoopRun`. So the main loop is the standard AppKit default-mode loop; event-tracking loops (live resize, menu tracking, drags) nest inside it as usual.

**Observed — scheduling APIs.**
- `PlatformDispatcher` (`platform.rs:1544-1575`): `dispatch` (GCD global queue by priority), **`dispatch_on_main_thread`** (`DispatchQueue::main().exec_async_f`, `gpui_apple/src/dispatcher.rs:52-57`), `dispatch_after` (GCD `exec_after_f` on a high-priority global queue, `:59-67`), `dispatch_on_main_thread_when_idle`, `prevent_app_nap`.
- Executors (`crates/gpui/src/executor.rs`): `ForegroundExecutor::spawn` (not `Send`, main thread only, `:27-35,378`), **`ForegroundExecutor::to_send()` → `SendForegroundExecutor::spawn(Send future)`** — enqueues onto the main thread *from any thread* (`:37-51,318`); `BackgroundExecutor::spawn/timer`; `ForegroundExecutor::spawn_when_idle(timeout, fut)` (`:409`). App-level: `App::spawn`, `Context::spawn`/`spawn_in`, `App::defer`, `Window::defer`, `Window::on_next_frame`, `Window::request_animation_frame` (`app.rs:2557-2588`, `window.rs:2931,3032-3052`).
- **No hook for run-loop modes.** `grep` for `NSEventTrackingRunLoopMode|NSModalPanelRunLoopMode` in `gpui_macos`/`gpui_apple` finds nothing; the only run-loop mode GPUI uses is `NSRunLoopCommonModes` for its `CAMetalDisplayLink` (`gpui_apple/src/display_link.rs:82`). The `Platform` trait has no "add run-loop source/observer" method. An app can nevertheless call Core Foundation directly on the main thread (`CFRunLoopGetMain`, `CFRunLoopAddSource/Timer` in `kCFRunLoopCommonModes`) — gpui-cef does.
- **Live resize:** `GPUIView` overrides `setFrameSize:` (updates drawable size, fires resize callback, `window.rs:3456-3491`) and `displayLayer:`, which **synchronously runs a frame with `presentsWithTransaction = true`** while stopping/restarting the display link (`window.rs:3494-3512`), so GPUI itself keeps painting during live resize. Whether `dispatch_on_main_thread`/GCD-main-queue work runs during a tracking-mode nested loop is Apple behaviour not documented in GPUI — **Inferred** that it does (libdispatch main queue is serviced via the main run loop's common-modes source), unverified → spike U4.

**Observed — what CEF needs and what the one prototype did.** CEF `master`: `OnScheduleMessagePumpWork(int64 delay_ms)` "may be called from any thread" and the sample external pump (`tests/shared/browser/main_message_loop_external_pump_mac.mm:134,153-165`) marshals to the main thread (`performSelector:onThread:`) and adds its `NSTimer` to **both `NSRunLoopCommonModes` and `NSEventTrackingRunLoopMode`** (`raw.githubusercontent.com/chromiumembedded/cef/master/…`, fetched 2026-11-18) — consistent with the bezier note. gpui-cef:
- **Did not use GPUI's executor.** Comment in `platform/cef/pump.rs:1-20` (gpui-cef@6b6a1d0): the first attempt via `cx.spawn` + `background_executor().timer()` ran "one tick every one to five seconds" when the app was idle ("**Reported/author-observed**, I did not reproduce"), and it is circular (no pump → no frame → no repaint → no executor tick). It installs a **`CFRunLoopTimer` + thread-safe `CFRunLoopSource` in `kCFRunLoopCommonModes`** on the main run loop (`pump.rs` imports `kCFRunLoopCommonModes`, `CFRunLoopSourceCreate`; `on_tick` calls `cef::do_message_loop_work()`), a 60 Hz fallback clamped to ≤17 ms delay, and a re-entrancy guard because calling `do_message_loop_work()` while GPUI's `App` is borrowed makes GPUI paint callbacks re-enter and panic with "RefCell already borrowed" (`pump.rs:~295-305`).
- Latency measured by the author: median 15.3 ms (naive timer) → 0.24–1.1 ms (signal-driven) over 100 samples, Apple M1 Pro, macOS 27.0.1, debug build (`docs/message-pump-performance.md`) — **Observed text, author-measured, not reproduced**.
- `NSApp` conflict: whichever class first calls `sharedApplication` wins; CEF must be initialised *after* GPUI has created `GPUIApplication`, and CEF's `CefAppProtocol` conformance must be retrofitted onto GPUI's class via ObjC runtime (`objc_allocateProtocol`, `class_addMethod`, swizzling `sendEvent:`) (`platform/cef/nsapp.rs`; README "Fighting over NSApplication / CefAppProtocol") — **Observed**, hacky but works for that project. GPUI exposes no hook to subclass or configure `NSApplication` (**Observed**: `APP_CLASS` is a fixed `GPUIApplication` ClassBuilder, `platform.rs:70`).
- **Inferred design for Aeri:** `OnScheduleMessagePumpWork` → store deadline atomically → `CFRunLoopSourceSignal` + `CFRunLoopWakeUp(main)` (or `SendForegroundExecutor::spawn` for the non-timing-critical hop) → main-thread callback runs `CefDoMessageLoopWork()` **outside any GPUI `App` borrow** (i.e. from a raw CF source/timer, not from inside `cx.update`). Modal AppKit loops (menus via `NSMenu`, sheets) still starve a default-mode-only pump; GPUI native menus go through `NSMenu` (`set_menus`, `platform.rs:380-430`), so a Common+EventTracking source is required.

## Q7. Input: keyboard, IME, focus model

**Observed — GPUI's macOS input is implemented on the content `NSView`.** `GPUIView` overrides `performKeyEquivalent:`, `keyDown:`, `keyUp:`, `flagsChanged:`, mouse/scroll/magnify/swipe, and the full `NSTextInputClient` set: `validAttributesForMarkedText`, `hasMarkedText`, `markedRange`, `selectedRange`, `firstRectForCharacterRange:actualRange:`, `insertText:replacementRange:`, `setMarkedText:selectedRange:replacementRange:`, `unmarkText`, `attributedSubstringForProposedRange:`, `doCommandBySelector:`, `characterIndexForPoint:` (`gpui_macos/src/window.rs:109-270`). `handle_key_event` (`:2815-2965`) routes: IME-first when composing or when an IME input source is active and the focused element's input handler prefers it; otherwise GPUI keybinding dispatch (`event_callback`); unhandled → `inputContext.handleEvent:`. Key equivalents (Cmd-…) are *not* given to the IME. `acceptsFirstMouse:` is implemented (`:3757`). Menu key equivalents: `set_menus(menus, keymap)` creates `NSMenuItem`s with `keyEquivalent` + modifier mask from the single-keystroke GPUI binding (`platform.rs:395-430`) — **so Cmd-shortcuts bound to menu items are handled by AppKit's menu before/independent of the first responder**. Multi-stroke bindings are not mapped to menu equivalents.
- **GPUI focus model** is internal (`FocusHandle`, `track_focus`, key contexts, actions; `crates/gpui/docs/key_dispatch.md`). It is orthogonal to AppKit first responder: GPUI's window has exactly one first-responder view (`GPUIView`), set at creation (`window.rs:1274`).

**Native child takes first responder — what happens (Inferred from AppKit semantics + wry code, not tested):**
- Key events go to the child (`keyDown:` on the first responder). GPUI never sees them unless the child doesn't handle them and forwards via the responder chain (the child's `nextResponder` is its superview chain; `GPUIView` sits there if the child is its subview — **Inferred**).
- `performKeyEquivalent:` is offered by AppKit to the key window's view hierarchy (and `NSApp.mainMenu`), so Cmd-shortcuts registered as NSMenu items still fire (that part is **Observed** only for the menu construction; the dispatch order is Apple behaviour — spike U6). Non-Cmd GPUI actions (plain keys, Ctrl-chords, multi-stroke) bound only in GPUI's keymap would **not** fire while a WKWebView/CEF NSView is first responder.
- Handing focus back: wry's `focus_parent()` does `window.makeFirstResponder(Some(&self.ns_view))` where `ns_view` is the GPUI view (`wry@4b2f030 src/wkwebview/mod.rs:1136-1142`); gpui-webview calls it on a click outside the webview's bounds (`WebViewElement::paint`). So the convention is: GPUI→native on click inside the native bounds (AppKit does this itself); native→GPUI by explicit `makeFirstResponder`. Cydonia also had to bind edit keys (Cmd-C/V → `copy:`/`paste:` responder actions) because WKWebView only accepts them as responder actions (cydonia blog) — **Reported**.
- **With OSR (gpui-cef)** GPUI stays first responder and *forwards* input to CEF: `platform/cef/input.rs` (701 lines) translates GPUI events to CEF key/mouse events; `ime.rs` (302 lines) implements GPUI's `EntityInputHandler` against CEF `ImeSetComposition/ImeCommitText/ImeCancelComposition` and positions the candidate window from `OnImeCompositionRangeChanged`; README: "Input methods are wired up… but the live round trip has not been confirmed by a human at a keyboard"; "No drag and drop between the page and the rest of the application"; the CEF keyboard handler must swallow native fallback because CEF otherwise replays keys into `NSMenu.performKeyEquivalent:` (README "Text input and input methods") — **Observed README statements by the author; automated NSTextInputClient→GPUI→CEF tests exist (`just input-e2e`), human IME validation absent**.
- **Windows:** GPUI handles IME via its own `gpui_windows/src/events.rs`/`keyboard.rs` (not read in depth by me — **Unknown depth**); child HWND (WebView2/CEF) gets Win32 focus and keyboard messages itself. `Inferred`: same split as macOS.

## Q9. Idle cost: redraw only when notified?

**Observed — GPUI draws only when dirty; macOS pacing link pauses when idle.**
1. **Demand-driven drawing.** `Window` keeps a `WindowInvalidator` with a `dirty` flag set by `Context::notify`/`Window::refresh` (`window.rs:123-270`). In the platform "request frame" callback (`window.rs:1904-2130`): `should_draw = invalidator.is_dirty() || force_render`; if not dirty, no `window.draw`. Presentation without redraw happens only for `needs_present` (animations/high-rate input/required presentation). Frames are pre-throttled: inactive default ≈30 fps, Low Power ≈30 fps, thermal-serious ≈60 fps (`WindowOptions::{inactive_frame_interval, low_power_frame_interval, thermal_frame_interval}`, `platform.rs:2680-2700`). Follow-up frames are requested only if dirty, next-frame callbacks pending, or a scene animation is active (`window.rs:2108-2122`).
2. **macOS 14+: the display link itself pauses.** `MetalFrames::end_frame` pauses the `CAMetalDisplayLink` "after any update in which GPUI neither drew, presented, nor asked for another frame, so an idle window acquires no drawables"; `wake()` unpauses when GPUI invalidates (`gpui_macos/src/display_link.rs:296-358`, `window.rs:2209-2222`). The link is also detached when the window is occluded (`start_display_link` bails if not `NSWindowOcclusionState::Visible`, `window.rs:878-885`).
3. **macOS <14:** shared `CVDisplayLink` per display runs while any window subscribes; ticks while idle are cheap no-ops ("Idle display-link ticks must neither consume a frame slot…", `window.rs:~2000`). **Observed** design; cost not measured.
4. **Windows is different:** a dedicated `VSyncProvider` thread loops on `DwmFlush()` and calls `RedrawWindow(hwnd, RDW_INVALIDATE)` for every visible, non-minimised window **each vsync** (`gpui_windows/src/platform.rs:429-490`, `vsync.rs`), so WM_PAINT + the request-frame callback fire every vsync even when nothing is dirty (the callback then skips drawing). Idle wakeups at display rate ×(windows) on Windows — **Inferred** cost: small CPU but a constant timer-like wakeup; not measured → spike U5. No pause when idle is visible in that loop (it stops only on `stop` flag/no windows).
5. **Observed counter-evidence to the "zero idle cost" claim:** any continuous animation (`with_animation(...repeat())`, `request_animation_frame`, a video/`surface`) keeps frames going; gpui-cef reports idle ≈1.2% CPU total (all processes, debug) because CEF drives itself at `frame_rate` plus the 60 Hz pump timer fallback (`pump.rs` `INTERVAL = 1/60`) — **an app that runs a fixed 60 Hz CEF pump does not idle at zero regardless of GPUI**.
6. **Third-party measurement (Reported):** gpui-fast's README claims upstream GPUI uses 5–6 ms main-thread CPU/frame when scrolling/animating its showcase vs 0.4–1.3 ms for the fork (Linux, 144 Hz, release) — a vendor-run benchmark of a fork; relevant only as evidence that GPUI's full-tree redraw cost per frame is not negligible for large UIs. Aeri's chrome (sidebar + address bar) is small, so **Inferred** negligible, to be measured.

## Implications for Aeri

1. **GPUI itself fits "native UI over an external engine" only partially, and the key blocker is z-order, not licensing.** A CEF *windowed* child NSView/HWND will always sit above everything GPUI draws (Q4). The slide-in sidebar/address bar "over the page" therefore needs one of: (a) OSR + GPUI texture (works today in gpui-cef on macOS; CPU copy; Alloy-only; you re-own input/IME/DnD — Q5/Q7); (b) a composition layer (gpui-fast fork or unmerged zed#62379; wry+WKWebView proven, CEF unproven); (c) a separate transparent overlay window (unproven for GPUI); (d) accept "beside, not over" (stock GPUI, zero risk). This interacts with the extension requirement (CefResearch): OSR/`parent_view` on macOS reportedly forces Alloy style, which per the bezier note weakens extension UI — decide the engine mode first, then the GPUI integration.
2. **Windows has no GPU-texture path in GPUI at all** (`draw_surfaces` is a no-op; no D3D shared-surface primitive). If the macOS answer is OSR-into-GPUI, the Windows story differs (child HWND always on top after zed#66368, overlays impossible, or CPU-copy `img()`). Plan Mac-first honestly: the architecture that works on macOS will not transfer unchanged.
3. **Distribution decision needed now.** Stock choices: (i) git dependency on `zed-industries/zed` pinned by commit (current, breaking-change-prone, multi-repo git fetches, must mirror `[patch]`); (ii) `gpui-pre` weekly community snapshots from crates.io (easy pins; third-party publisher); (iii) crates.io `gpui` 0.2.2 (13 months stale, doesn't match current docs/examples). Budget for **vendoring/pinning and periodic upgrades**; at ~37 GPUI-crate commits per 16 days a rebase is a recurring cost. A small patch set (e.g. BGRA `surface()`, composition) means maintaining a fork or waiting for upstream — neither PR is merged.
4. **Run loop is workable but non-idiomatic.** CEF `external_message_pump` is feasible with raw CF sources in CommonModes + EventTracking, outside any GPUI `App` borrow; the `NSApplication`/`CefAppProtocol` retrofit via ObjC runtime is required and fragile. Don't schedule CEF work via GPUI's executors (author-observed starvation when idle).
5. **Idle cost story is good on macOS 14+** (link pauses; draws only on notify) **but not on Windows** (per-vsync invalidation) and not if CEF is pumped at a fixed 60 Hz. Fine for a "lighter than Helium" claim only if measured per-profile.
6. **Input:** GPUI's macOS input stack is solid (NSTextInputClient, IME-aware key routing). Under windowed CEF, the engine owns text input and GPUI shortcuts must be NSMenu key equivalents or handled via CEF key callbacks. Under OSR, Aeri owns IME bridging (gpui-cef has a reference implementation, human-unvalidated).
7. **Window shell features are covered:** hidden/transparent titlebar + custom traffic-light position, transparent/blurred backgrounds, native fullscreen, multiple windows, spring/easing animation (Q8). Multiple profile windows in one process are the native model.
8. **Licensing is clean for Aeri** (Apache-2.0 GPUI; no strong copyleft in the closure; MPL-2.0 for `option-ext`/`dwrote`/build-time `cbindgen` only — keep their notices, no source-sharing impact for Aeri's own code).
