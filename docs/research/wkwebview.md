# WKWebView / WebKit as Aeri's engine on macOS: evidence against the approved requirements

Research date: 2026-11-18. Author: WebKitRouteResearch (worker agent). Extends `docs/research/{cef,gpui,blocking-and-credentials,codecs-drm}.md`; nothing those files establish is repeated, only cross-referenced.
Labels: **Observed** = read in a primary source at a named version/commit, or measured by me this session. **Reported** = secondary or third-party statement I could not verify. **Inferred** = my reasoning.
Sources are `[Sn]` and listed at the end with version/date. Windows/WebView2 is out of scope here (another agent).

## Method and what I actually ran

Machine: Apple M4 Pro, 24 GiB, macOS 27.2.1 (26B131), Xcode SDK 27.2, Swift 6.4.2. Single run per measurement, one machine, `example.com` as the only page. No benchmark here is a Chromium comparison (see Q5).

- Read the macOS 27.2 SDK `WebKit.framework/Headers` (WKWebExtension*, WKWebsiteDataStore, WKProcessPool, WKContentRuleListStore, WKURLSchemeHandler, WKUserScript, WKWebView) [S1].
- Cloned and read: `driceroland/Search` @ `c5870a6` (2026-11-18, v1.0.14) [S2]; `WebKit/standards-positions` @ `7ed1cc7` (2026-11-15) [S3]; `AdguardTeam/SafariConverterLib` @ `1cfdcaf` (2026-10-15) [S4]; `brave/adblock-rust` @ `1108c61` (v0.13.6) [S5]; `madsmtm/objc2` @ `8a5abac` (2026-10-17) and the published `objc2-web-kit-0.3.2` crate [S6]. Read WebKit source at `c05e47f` (HEAD on 2026-11-18): `ContentExtensionParser.cpp`, `ContentExtensionActions.h`, `UnifiedWebPreferences.yaml`, `NetworkProcessProxy.cpp`, `WKWebsiteDataStore.mm` [S7].
- Queried MDN browser-compat-data 8.1.9 (2026-11-12) for Chrome vs Safari support [S8]; Apple security-release list (fetched 2026-11-18) [S9]; WebKit blog posts for Safari 26.2, 26.4, 27.0, 27.1, 27.2, Adaptive Dark Mode [S10].
- **Probe app** (`/tmp/wkr/probe/main.swift`, ~190 lines, ad-hoc signed, no entitlements, Swift/AppKit, not a bundle with Info.plist): (a) JS feature/codec/EME report from a bare `WKWebView` at `https://example.com/`; (b) N views in N `WKWebsiteDataStore(forIdentifier:)` vs one shared store, with `ps` samples of the new `com.apple.WebKit.*` processes (baseline pids excluded); (c) cookie/localStorage/IndexedDB isolation and persistence across a relaunch; (d) `WKContentRuleListStore.compileContentRuleList` with N synthetic rules; (e) `WKWebView.handlesURLScheme`. All probe data stores and rule lists were removed afterwards, and so were the probe's `~/Library/WebKit/*` folders.
- Did **not** run: Search.app (only `du` and `defaults read` on it; no extension installs in the user's copy), Netflix/Spotify/Disney+ (no accounts), any Windows code, a Chromium memory comparison (my one headless Chrome 158 run launched six renderers for one URL and is not comparable; I discarded it).
- Harness bug worth knowing: touching a `WKWebView` off the main thread makes the app die with SIGKILL ("WKWebView APIs must be called from the main thread" followed by an unrecoverable exception in the system log); that was mine, not a WebKit finding.

## Headline findings

1. **WKWebView meets the media, profile-cost and size requirements better than CEF** (OS H.264/AAC/HEVC and a FairPlay key system with no custom build; one persistent isolated data store per UUID; shared Networking and GPU processes; ~11 MB app) and **fails three requirements that Aeri marked decisive**: Chrome site behaviour, uBO-quality built-in blocking, and Chrome Web Store extensions without a large compatibility layer.
2. **No public API intercepts arbitrary http(s) requests** (Observed). Blocking is a static JSON rule list, max 150,000 rules per list, with no scriptlets, redirects to neutered resources, `$removeparam`, `$csp`, `$header`, procedural cosmetics. adblock-rust's `content-blocking` converter and AdGuard's converter both drop those. Aeri's approved design (adblock-rust in the request path at ~3.9 µs, shared by all profiles) cannot be built on WKWebView.
3. **Chrome extensions run on WKWebExtension only with a large shim layer.** Search, the only reference, needs 12,030 Swift lines in 16 files (13% of its 91,033-line source) plus a ~229 KB injected JS prelude, and still lists open bugs for 1Password and Bitwarden. uBO Lite works after Search removes rules WebKit misreads.
4. **WKWebExtension supports one extension controller for the whole app in Search's design**; per-profile controllers are allowed by the API but untested. This is the exact place where Aeri's "extension data belongs to one profile" rule is at risk.
5. **A bare WKWebView is not Safari**: no `PushManager`, no `setAppBadge`, no conditional-mediation passkeys, a UA without a Safari token (Observed, Q1/Q8).

## Q2. Extensions on WKWebExtension

### 2.1 API surface (Observed, SDK 27.2 headers [S1]; Apple doc `WKWebExtension` [S13])

- Whole family is `API_AVAILABLE(macos(15.4))`. Created with `WKWebExtension(resourceBaseURL:)` pointing at "a directory or a ZIP archive" [S13]; **CRX is not accepted**, so the browser must fetch and unpack it.
- Permissions are a closed list of 16: `activeTab, alarms, clipboardWrite, contextMenus, cookies, declarativeNetRequest, declarativeNetRequestFeedback, declarativeNetRequestWithHostAccess, menus, nativeMessaging, scripting, storage, tabs, unlimitedStorage, webNavigation, webRequest`. No `bookmarks`, `history`, `downloads`, `sidePanel`, `offscreen`, `tabGroups`, `notifications`, `identity`, `management`, `proxy`, `privacy`, `userScripts`, `desktopCapture`, `tabCapture`.
- The embedder implements `WKWebExtensionControllerDelegate`: open windows/tabs, option pages, permission prompts, action popup presentation, `sendMessage:toApplicationWithIdentifier:` and `connectUsingMessagePort:` (native messaging; default is "no action" unless the extension came from a Safari app-extension bundle). Tabs/windows are the embedder's own objects behind `WKWebExtensionTab/Window` protocols.
- `WKWebExtensionContext.unsupportedAPIs` hides APIs for feature detection. Extension pages **must** use `context.webViewConfiguration`, and the app "must swap web views in tabs when navigating to and from web extension URLs". A `WKWebViewConfiguration` carries one `webExtensionController`, fixed at view creation.
- `WKWebExtensionControllerConfiguration` has `defaultWebsiteDataStore` (cookies for extensions' `cookies` API); "extensions can also access other data stores for any open tabs"; persistent unique configs via `configurationWithIdentifier:` ("each controller should use a unique configuration").
- WebKit 27.0 adds `runtime.getDocumentId()` and user-gesture propagation through `sendMessage/connect` [S10]. The 26.x posts list only Safari-side extension management APIs.

### 2.2 Can a third-party browser load Chrome Web Store CRX packages? Yes (Observed, Search v1.0.14 [S2])

- `Crx.swift` (245 lines): fetch from the Web Store's public update endpoint pretending to be Chrome `156.0.0.0` (1Password's popup only opens from Chrome 149; Web Store refuses minimum versions), parse CRX3, require a public key whose SHA-256 prefix equals the extension id and a valid signature over the zip, unpack into the app folder, hand the folder to WebKit. Unpacked folders get Chrome's path-derived id so native hosts accept them.
- `ExtensionShims.prepare` then **edits the verified package**: writes `search-shim.js` into the background and every extension page/content script, adds `nativeMessaging` (and `scripting` if `userScripts`) to the manifest, removes DNR rules WebKit misreads. MV2 is not a goal (Chrome removed MV2 from the store 2026-08-31 per `cef.md`).

### 2.3 Chrome APIs and behaviours Search had to supply or repair (Observed, `ExtensionShims.swift` 5,773 lines, `Extensions.swift` 2,537, plus 14 helper files)

- **Whole namespaces defined natively:** `bookmarks, history, downloads, sidePanel, offscreen, tabGroups, fontSettings, management, notifications, tts, identity (OAuth), search, idle, power, browsingData, sessions, topSites, readingList`; Chrome settings objects (`privacy`-style `setting.*`); `userScripts` (via registered content scripts); `desktopCapture/tabCapture` (own picker); the old `webkitRequestFileSystem` API; `runtime.getContexts`, `windows.update`. `proxy` is not available ("WebKit doesn't give it to extensions", ROADMAP).
- **Polyfills:** `Symbol.dispose`/`asyncDispose` (Bitwarden), `requestIdleCallback` (removed from WebKit, bug 287681; Proton Pass), `navigator.userAgentData`, `InstallEvent`, Chrome enums missing in content scripts, Chrome UA in workers.
- **Behaviour repairs:** multiple `onMessage` listeners (WebKit takes the first return value), replies to pages that never answer, listeners added after a worker starts, `clients.matchAll()` for popups, messages WebKit never delivers to extension pages (Bitwarden sync/passkey window), WebSockets in workers (WebKit freezes the worker; 1Password) moved to a native socket, `fetch` with credentials moved to the browser to carry `SameSite=Lax` cookies, worker recovery after crashes, one shared shim copy per frame (a 229 KB prelude was parsed 63 times per 20-frame page with 1Password).
- **DNR repairs:** rules with `regexFilter` + `requestDomains`, or `responseHeaders` conditions, are dropped from uBO Lite's rulesets (`misreadByWebKit`), because WebKit ignores the list/condition and applies the rest to every page (blank pages after ~30 s, GitLab bundles blocked).

### 2.4 Do the four target extensions work? (Reported from Search's own changelog/roadmap; I did not install anything)

| Extension | Evidence in Search v1.0.14 | Status |
|---|---|---|
| uBlock Origin Lite | `Tests/extension_ubol.py` (299 lines) exercises it; CHANGELOG fixes for blank pages (#709), GitLab bundles; ROADMAP: "uBlock blocks from the first second after launch" still open (#711). gorhill's own Safari list (2025-04) names `excludeMatches` ignored, `allowAllRequests`, `requestDomains` misread, regex rules rejected ("a lot of regex-based filters are rejected compared to Chromium"), strict blocking not working; several then "being addressed by Safari" [S14]. His comment: disabling/enabling for a site takes "long seconds" to take effect in Safari. | **Works with workarounds; weaker than on Chromium (Reported)** |
| Bitwarden | CHANGELOG: popup, passkey window, offscreen saves, self-hosted server, `Symbol.dispose`, native messaging for Touch ID unlock all needed fixes; ROADMAP open: "Bitwarden says WebAssembly isn't supported" on some Macs (#716). | **Works after many fixes; one open launch bug (Reported)** |
| 1Password | CHANGELOG: worker freeze on WebSocket, popup waits, crash on macOS 15, unlock only from Chrome 149+, 63× script parse, orphaned native helpers (#1036); ROADMAP open: sign-in unstable (#802), unlock doesn't open (#685); desktop-app unlock needs "Add Browser" in 1Password settings. | **Works, still unstable (Reported)** |
| Dark Reader | Only evidence: popup must load from its own address (a copy was refused; CHANGELOG 1.0.3) and Search ships its own page-darkening because of Dark Reader-like demand. No end-to-end report. | **Unknown (no evidence either way)** |

### 2.5 Native messaging (Observed)
WebKit offers only the delegate hooks above. Search's `ExtensionNative.swift` (372 lines) reads Chrome-format host manifests from Chrome, Chromium, Edge, Brave, Arc, Vivaldi, Opera folders, enforces `allowed_origins`, spawns the host with Chrome's framing and stops it with the worker. Hosts may refuse unknown browsers (its own header) and 1Password's desktop app needs the browser added in its settings (ROADMAP). So native messaging works **if the browser builds the whole protocol and password-manager vendors allow it**; it is not something WebKit does.

### 2.6 Cost to build and keep (Observed)
Extension code in Search: **12,030 lines** (`Extension*.swift` ×15 + `Crx.swift`) of **91,033** Swift lines; 161 Swift files; ~3.7k lines of that is the injected JS prelude (ROADMAP #997: ~229 KB). Nine Python harnesses + a Swift suite test it. 135 CHANGELOG lines out of 995 mention extensions; 29 name uBOL/Bitwarden/1Password/Proton/NordPass. All of it landed between 2026-09-23 (v1.0) and 2026-11-17 (v1.0.14), i.e. 15 releases (1.0 to 1.0.14) in eight weeks by one small team plus contributors, and still the roadmap lists Eagle, NordPass, Todoist, Box Tools, Ghostery misses, VPN/proxy extensions, ChatGPT side panel cookies as open. **Inferred:** this is a standing maintenance liability, not a one-time port.

## Q3. Profiles

- **Observed (SDK header [S1], WebKit source [S7], my probe):** `WKWebsiteDataStore(forIdentifier: UUID)` (macOS 14+) is persistent and stored per identifier under `~/Library/WebKit/<bundle>/WebsiteDataStore/<uuid>/`. Cookies, localStorage and IndexedDB set in store A were invisible in B, C (probe: `cookie=[] ls=null idb=undefined`), and survived a relaunch (`cookie=[k=P] ls=P`). `identifier`, `fetchAllDataStoreIdentifiers`, `removeDataStore(forIdentifier:)` (error if a WKWebView still uses it) exist; `proxyConfigurations` per store (14+); `fetchData(of:)`/`restoreData` export/restore arrives in macOS 26 only.
- **Limits:** the store is the isolation unit for cookies, cache, IndexedDB, service workers, Cache API and permissions *as WebKit keeps them*; sites' permission prompts (camera, location, notifications) are decided by the **embedder's** delegates, so Aeri stores them itself (as Search does with "capture.*" keys). The store is bound when the view is created: moving a tab to another profile means rebuilding the view with `interactionState` (Search `Tab.rehome`). A deleted store requires every view released first.
- **Processes (Observed):** WebKit has one default `NetworkProcessProxy` per app on Cocoa (`ensureDefaultNetworkProcess`, `WebsiteDataStore::networkProcess()` [S7]); `WKProcessPool` "multiple instances no longer has any effect" since macOS 12 [S1]; "each web view is given its own web content process until an implementation-defined process limit is reached" [S1]. My probe: 1, 5 and 10 stores each gave **one** `com.apple.WebKit.Networking` and **one** GPU process; WebContent was one per view in both shared-store and per-store runs (so I could not show store→process separation; the header contract is what governs).
- **Cost (Observed, single run, `example.com`, RSS):**

| Run | WebContent | Networking | GPU | App process |
|---|---|---|---|---|
| 1 view, 1 store | ×1 36.0 MB | 14.8 MB | 28.6 MB | 87.2 MB (66 MB before any view) |
| 5 views, 1 shared store | ×5 180.5 MB | 15.1 MB | 35.7 MB | 92.5 MB |
| 5 views, 5 stores | ×5 172.1 MB | 18.1 MB | 29.8 MB | 88.6 MB |
| 10 views, 10 stores | ×10 361.4 MB | 24.9 MB | 37.4 MB | 95.4 MB |

  The **per-profile overhead beyond its pages is about 0.5–1 MB in Networking and ~3 MB in the app process** (5 stores vs 1); the 36 MB per page is the page. Releasing the views removed every WebContent process immediately; Networking and GPU stay. **Inferred:** a dormant profile costs only its on-disk store. `cef.md` has no equivalent measurement (it says per-profile cost "must be measured"), so this is better evidence than any CEF number we hold, though not a Chromium comparison.
- **Extensions per profile (Observed, Search):** extensions belong to a `WKWebExtensionController`, not to a data store. Search uses **one controller for the whole app**, pointing at the Personal profile's store, and documents why: "one per profile would run each extension's worker once per profile" (`Profiles.swift` header); ROADMAP: "Extensions per space ... WebKit has one extension controller for the whole app, so this means one per space" (deferred). So in the only reference app, extensions and their storage are **shared across profiles**. The API does allow a controller per profile with `configurationWithIdentifier:` (header, Observed). **Unknown:** whether per-profile controllers work with Bitwarden/uBOL, what each costs (a service worker per extension per profile), and how cookie-reading extensions behave.

## Q4. Content blocking

- **Capacity (Observed):** WebKit `ContentExtensionParser.cpp` @ `c05e47f`: `constexpr size_t maxRuleCount = 150000;` → `JSONTooManyRules`. My probe: 150,000 simple third-party host rules compiled in **0.50 s** (JSON 20 MB); 150,001 failed with "Too many rules in JSON array". 50,000 path rules 0.12 s; 50,000 `if-domain` cosmetic rules **1.84 s**. Synthetic, trivial regexes; real EasyList-converted lists compile slower. Total number of lists and combined memory: not measured (Unknown).
- **Expressiveness (Observed, parser):** triggers `url-filter` (limited regex), `resource-type`, `load-type`, `load-context`, `request-method`, one condition among `if/unless-domain`, `if/unless-top-url`, `if/unless-frame-url`; actions `block`, `block-cookies`, `css-display-none`, `ignore-previous-rules`, `make-https`, `notify`, plus `redirect`/`modify-headers` parse paths. Compile errors seen in my probe: unsupported regex ("Internal error in YARR").
- **What converters lose (Observed):** adblock-rust's `content_blocking` module (feature `content-blocking`, v0.13.6 [S5]) lists failures: `NetworkRedirectUnsupported`, `NetworkGenerichideUnsupported`, `NetworkBadFilterUnsupported`, `NetworkCspUnsupported`, `NetworkRemoveparamUnsupported`, `FullRegexUnsupported`, `CosmeticEntitiesUnsupported`, `ProceduralCosmeticFiltersUnsupported`, scriptlet injection, `:style()`, `if-domain`+`unless-domain` together. AdGuard SafariConverterLib [S4] "not supported": `$header $csp $redirect $redirect-rule $removeparam $removeheader $replace $cookie $jsonprune $urltransform $to $strict-first-party` etc.; cosmetics beyond basic selectors, scripts and scriptlets "can only be interpreted by a separate extension"; "with Safari there will always be a slight delay" for scriptlets.
- **How Brave iOS does it (Observed/Reported):** Brave builds both an adblock-rust engine and a WebKit content rule list from the same lists (crash reports from Brave iOS show `GroupedAdBlockEngine.compile` and `ContentRuleListStore` compile paths); an open issue (#56891, Jul 2026, AI-drafted from crash logs) shows OOM aborts compiling large custom lists on iOS. iOS memory limits do not apply on macOS, but it shows compile cost is real.
- **Request interception (Observed, confirmed):** `WKURLSchemeHandler` is for custom schemes only: the header says registering a handler for a scheme "WebKit handles internally" throws; `WKWebView.handlesURLScheme` returned **true for http, https, ws, wss, ftp, file, data, blob, about** and false for custom names (probe). `WKNavigationDelegate.decidePolicyFor` sees navigations (and responses), not subresources, XHR, fetch or WebSockets. **There is no public API to intercept arbitrary http(s) requests.** `WKWebExtension` `webRequest` is exposed as a permission (blocking support is WebKit's, unverified by me). Orion (closed source) documents a "Resource Interceptor" for the webRequest API and runs uBlock Origin; its mechanism is unknown (**Reported**) [S15].
- **Cosmetic injection (Observed):** `WKUserScript` has only `atDocumentStart` ("after the document element has been created, but before any other content has been loaded") and `atDocumentEnd`; `forMainFrameOnly:` and `WKContentWorld` selectable. There is **no public `WKUserStyleSheet`**: CSS goes in via a script that adds a `<style>`, or via `css-display-none` rules (Search's hidden-element feature uses a start-time injection). So uBO-style procedural and scriptlet filters would need an own engine in a start-time user script, with no way to get filter matches from the network layer.
- **Inferred:** WebKit cannot meet "uBO list quality" for the built-in blocker. A converted EasyList/uBO set would be a lossy subset; Orion's own docs say its built-in blocker is "about 90% as efficient as uBlock Origin" and recommend running uBO on top [S15] (**Reported**, vendor claim).

## Q5. Performance and resource control

- **Process model (Observed):** every app launches its own WebKit XPC processes (`com.apple.WebKit.WebContent`, `.Networking`, `.GPU`): my probe's pids were all new relative to a baseline with no other WebKit processes, so nothing is shared with Safari. One Networking and one GPU process per app (see Q3). WebContent per view until an implementation limit [S1].
- **Memory per tab versus Chromium:** **no primary head-to-head measurement found.** My WebKit-only number is ~36 MB RSS per `example.com` page. Search's own comment says "a hundred to three hundred megabytes" for a real page and "five heavy tabs held about 800 MB after their window closed, now about 70 MB" (CHANGELOG, **Reported**). RSS double counts shared pages; use `footprint` in the spike. `cef.md` has no number either.
- **App size (Observed):** `Search.app` v1.0.14 = **11 MB** on disk (`du -sh`), README "about 10 MB"; macOS 14 floor. My bare probe binary is 155 KB. CEF's framework alone is 341 MB (`cef.md`). Aeri on WebKit would be a few MB of Rust + GPUI.
- **Suspend/discard (Observed):** no public discard API. `pauseAllMediaPlayback`, `setAllMediaPlaybackSuspended`, `closeAllMediaPresentations`, `requestMediaPlaybackState` (macOS 12) exist; `interactionState` (12) captures back/forward and scroll. Search's "rest" is: save `interactionState`, store a snapshot, **deallocate the WKWebView** (`Tab.sleep` → `discard()`), rebuild lazily, with idle timers (30 min, 10 min, 2 h), memory-pressure source (5 min on warning, 0 on critical) and exemptions (audio, calls, downloads, unsent input). My probe confirmed deallocation removes the WebContent process at once.
- **Per-WKWebView memory/CPU (Observed):** none public. KVC `_webProcessIdentifier` (private) returned the WebContent pid in my probe and in Search's test bench only; one can then call `proc_pid_rusage`/`ps`. GPU and Networking processes are shared, so GPU memory cannot be attributed to a tab; extension background workers run in their own views and need their own accounting. CEF has a public `CefTaskManager` (CPU, memory, GPU memory per task) per `cef.md`. **This is a requirement where CEF is clearly better.**
- **Hidden/occluded throttling (Observed in source):** WebKit defaults on Cocoa: `HiddenPageDOMTimerThrottlingEnabled` = true, `HiddenPageCSSAnimationSuspensionEnabled` = true, `PageVisibilityBasedProcessSuppressionEnabled` = true (`UnifiedWebPreferences.yaml` @ `c05e47f` [S7]). A view removed from the window or hidden is treated as not visible: Search saw a video call freeze for that reason (Q1). Exact rates were not measured. `WKWebView` has no public "occluded" setter; Search uses a private `_setWindowOcclusionDetectionEnabled:` in its test bench only.

## Q6. GPUI integration (existing evidence, nothing re-measured)

- **Observed in `gpui.md` Q4 [S16]:** WKWebView is a native child `NSView`, so under stock GPUI it covers GPUI drawing, including slide-in panels, popovers and tooltips in its bounds. **wry** (`wry@4b2f030` `src/wkwebview/mod.rs`) builds a `WKWebView` as a child of GPUI's `NSView` via `HasWindowHandle`; `longbridge/gpui-component` ships `gpui-webview` on top of it (uses `lb-wry 0.53.3`). Layout sync is a custom GPUI element calling `set_bounds` in `prepaint`.
- **Overlays:** with the third-party **`gpui-fast`** composition fork (`enable_window_composition`, ported from open Zed PR #62379), `gpui-webview` reparents the `WKWebView` into a composition surface, giving "GPUI overlays render above the page" on macOS; stock GPUI does not. WKWebView is a plain layer-backed NSView, so the transparent-child-window route (also in `gpui.md` U2) applies equally and is the same spike. **Inferred:** a slide-in sidebar works under composition, or as a sibling beside the page, or as a transparent child `NSWindow` above it, as for any NSView.
- **Run loop:** nothing special. WKWebView has no external pump; GPUI owns `[NSApp run]` and WebKit's own work runs on its processes and the main run loop. This removes `CefAppProtocol`, the CF-source pump and NSApplication swizzles that `gpui.md` Q6 says CEF needs. **Inferred:** keyboard routing still needs the first-responder handling described in `gpui.md` Q7 (`makeFirstResponder`, NSMenu key equivalents for Cmd shortcuts, Cydonia's `copy:`/`paste:` finding [S16]).
- **Prior art risk:** Cydonia (a third-party GPUI browser, 2026-09-28) hit overlay and drag problems and used snapshot-and-offscreen tricks [S16] (**Reported**).

## Q7. Media

- **Observed (probe, WKWebView macOS 27.2.1, no entitlements):** `canPlayType` "probably" for H.264 (baseline, high), HEVC (`hvc1`), AAC, E-AC-3, VP9, VP09 in MP4, AV1, Opus; MP3/FLAC "maybe"; `MediaSource`/`ManagedMediaSource` accept all of those (FLAC false). So H.264/AAC/HEVC are free of any codec licensing work for Aeri (the OS supplies them), a direct contrast to `codecs-drm.md` for CEF.
- **EME (Observed):** `requestMediaKeySystemAccess` **resolves** for `com.apple.fps` and `com.apple.fps.1_0` (FairPlay) and `org.w3.clearkey`; **rejects** `com.widevine.alpha` and `com.microsoft.playready` ("NotSupportedError"). Access resolving does not prove a license exchange; I did not run one.
- **FairPlay in a third-party WKWebView browser (Reported):** the open-source browser Cra routes Spotify, Netflix, Disney+, Max, Prime Video, Hulu, Apple TV, Tidal, Deezer and others to a WebKit page "because macOS gives every app FairPlay"; its note says "a plain, ad-hoc-signed test app with no entitlements played EZDRM's public FairPlay stream end to end (certificate, license request, license, keys usable, 720p playing)" [S17]. That is consistent with my EME result. It also documents the CEF-side failure (Widevine without VMP: Spotify 403/500, Disney+ error 83, Netflix refuses or plays low quality), matching `codecs-drm.md`.
- **Netflix in Orion/Search (Reported):** an Orion user reports DRM works but titles show "HD" only; another says 4K works with high CPU on M1 Pro (Reddit r/OrionBrowser, 2025-08-14) [S18]; Netflix's own page [S12] says macOS 4K is Safari. Search's CHANGELOG mentions Netflix subtitles over a floating video (1.0.x), implying playback works. **Inferred:** 1080p-class playback is plausible; 4K is not guaranteed outside Safari. **Unknown:** Spotify/Disney+ with Search/Orion (I found no primary statement).

## Q8. Passwords and passkeys

- **AutoFill (Observed):** `Search`'s `ApplePasswords.swift` header: "There is no public way for a browser to ask the Mac's Passwords app for a site's accounts: AuthenticationServices hands an app only its own associated domains' passwords, and WebKit's AutoFill is Safari's." Confirmed consistent with `blocking-and-credentials.md` Observed #4. A WKWebView embedder gets **no** Apple Passwords AutoFill; Search builds its own form relay, Keychain store, import tools; it can also run Apple's native-messaging helper for "iCloud Passwords" only because it is a build with the browser entitlement (see `blocking-and-credentials.md` Observed #3).
- **Passkeys (Observed, Apple doc [S19], probe):** Apple says a browser app that uses `WKWebView` has WebKit "automatically handle" WebAuthn challenges, and that the person decides whether the app may access passkeys via `ASAuthorizationWebBrowserPublicKeyCredentialManager`. In my unentitled probe `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()` = **false** and `isConditionalMediationAvailable()` = **false**, with `navigator.credentials` and `PublicKeyCredential` present. Search gates its passkey UI on `SecTaskCopyValueForEntitlement(…"com.apple.developer.web-browser.public-key-credential")`, ships a second entitlements file and provisioning profile for the passkey build, and does the ceremony itself through `ASAuthorizationWebBrowserPlatformPublicKeyCredential*` because, left to WebKit, conditional-mediation requests leave an AuthenticationServicesAgent operation that can wedge until reboot (`Passkeys.swift` header). **The same Apple-restricted entitlement (organisation Account Holder) that blocks Aeri's individual account on CEF (`02-tech-stack.md`) is needed on WKWebView for platform passkeys**; the entitlement does not go away by choosing WebKit.
- **ASAuthorization (Observed):** usable from Rust only through objc2 bindings of AuthenticationServices; Apple's docs frame it as the API for browsers that do **not** use WKWebView ("If your browser app uses an alternative web browser engine…"), while Search shows it is also the practical path for WKWebView browsers.
- **Extensions:** password-manager extensions run (Q2.4) and answer passkey requests themselves; Search had to patch `navigator.credentials` ordering for them (CHANGELOG 1.0.x).

## Q9. Maintenance and security updates

- **Engine updates (Observed, Apple security list fetched 2026-11-18 [S9]):** WKWebView uses the system WebKit. Security fixes ship in OS updates and Safari updates for older OS: **macOS Golden Gate 27.2.1, Tahoe 26.7.3, Sequoia 15.8.3 on 2026-11-09**; **Safari 27.2** (2026-10-26) lists "macOS Sequoia and macOS Tahoe"; **Sonoma 14.8.9** was last updated 2026-08-06, and Safari 26.6.1 (2026-08-18) was the last Safari for Sonoma. **Inferred:** WKWebView apps pick up WebKit fixes through those updates; **Inferred:** Sonoma users have received no WebKit fix since 2026-08-06.
- **Minimum macOS:** `WKWebsiteDataStore(forIdentifier:)` 14.0; `WKWebExtension*` 15.4; `fetchData(of:)`/`restoreData` 26.0 [S1]. Extensions as a first-release requirement therefore set the floor at **macOS 15.4**, which is a patched OS line today. GPUI's floor (macOS 14, `02-tech-stack.md`) would no longer be the binding one. Search itself targets 14 and turns extensions off below 15.4.
- **Feature level follows the user's OS (Observed):** Search reports "the Safari version this Mac has" to sites after a bug where it claimed 26.5 on an older macOS. A Safari-27.3-only feature such as Adaptive Dark Mode [S10] will not exist on all users' systems; whether WKWebView exposes it is **Unknown** (no SDK 27.2 API found).
- **Deltas versus CEF (`cef.md` §1):** no monthly framework to ship, no codec build, no CEF API pin. Instead: private-API use, tracking WebKit regressions in extensions across OS versions (Search's changelog repeatedly cites WebKit bugs "fixed upstream, comes with a macOS update"), and an ever-growing shim.

## Q10. Rust access (objc2-web-kit)

- **Observed:** `objc2-web-kit` **0.3.2**, published 2025-10-04 (licence `Zlib OR Apache-2.0 OR MIT`, MSRV 1.71), 24.8 M downloads, owners `madsmtm`, `simlay`; repo `madsmtm/objc2` (main @ 2026-10-17, bindings regenerated from Xcode 27.1 SDK per `crates/objc2/src/lib.rs`, core `objc2` 0.6.5 released 2026-10-05). The framework crates (`objc2-app-kit`, `-foundation`, `-web-kit`) were **last published 13 months ago** and have no release carrying the 2026 SDK. [S6]
- **Observed coverage in 0.3.2 (generated files present):** `WKWebView`, `WKWebViewConfiguration`, `WKWebsiteDataStore` (incl. `dataStoreForIdentifier`, `removeDataStoreForIdentifier`, `identifier`), `WKContentRuleList`, `WKContentRuleListStore` (`compileContentRuleListForIdentifier_…`), `WKURLSchemeHandler/Task`, `WKProcessPool`, `WKHTTPCookieStore`, and all 16 `WKWebExtension*` modules (classes/protocols) including `WKWebExtensionController` (`initWithConfiguration`, `setDelegate`, `loadExtensionContext_error`) and `…ControllerDelegate`; per-class cargo features. 215 generated modules. It includes the macOS 26 `fetchDataOfTypes`/`restoreData` methods, so the generated SDK level is about Xcode 26.0 (Inferred from the date); anything newer needs git `main`.
- **Inferred:** usable today for views, stores, rule lists and extension plumbing, but implementing the Objective-C delegate/tab/window **protocols** from Rust needs `define_class!` boilerplate (≈ what Search's 2.5k-line `Extensions.swift` is). The generated types are `MainThreadOnly`. A git dependency on `objc2` main is possible if newer SDK symbols are needed. For `wry` (Tauri, 0.57.2 published 2026-11-10) as a ready-made `WKWebView` host, see `gpui.md`; wry exposes no extension controller.

## Implications for Aeri

1. **WKWebView on macOS does not satisfy the three requirements the owner put first** (Chrome behaviour, CWS extensions at low cost, uBO-quality blocking). It wins on media, install size, profile storage cost and GPUI integration. The gap is structural: WebKit opposes four device APIs and offers no request interception.
2. **Do not adopt WKWebView as the base engine for the first public release** and keep the CEF decision of `02-tech-stack.md`. The CWS-extension requirement on WebKit means rebuilding what Search spent ~12k lines and weeks of fixes on, with no extension-per-profile story.
3. **If DRM streaming or codecs become the blocker on the CEF path, a narrow WebKit fallback is the cheaper option than a self-built CEF** (Cra does this, Reported [S17]): open a configurable list of DRM sites in a `WKWebView` window under a `WKWebsiteDataStore(forIdentifier:)` per profile. Costs: two engines, no shared cookies, no extensions on those pages, no Aeri blocker; entitlement still needed for passkeys. This is a product decision for the owner, not a Phase-1 task.
4. **If the owner prefers WebKit anyway** (Search-like product), the plan must change: drop "exactly as Chrome", accept Orion-style 90% blocking, accept lossy filter conversion, require macOS 15.4+, budget a Search-sized shim, and decide extension-controller-per-profile up front. Windows would need its own engine (WebView2) and the approved "same behaviour" promise would not hold.
5. **Passkey and Apple Passwords work is the same on both**: request the browser entitlement early with an organisation account.
6. **objc2-web-kit 0.3.2 is enough to spike** any WebKit work (stores, rule lists, extension controller), but Aeri would depend on a stale crate or git `main`.

## Unknowns that need a spike

1. **Per-profile `WKWebExtensionController`:** two profiles, same extension (Bitwarden, uBOL); memory per worker, data separation, cookie access via `defaultWebsiteDataStore`, popup routing. Pass/fail: separate storage and ≤ one extra worker per profile.
2. **Blocklist conversion at scale:** EasyList + EasyPrivacy + uBO filters through adblock-rust `content-blocking` and AdGuard's converter; measure rule count, split lists, compile time, resident memory of the Networking process, and coverage against the same list on adblock-rust natively (page corpus, ads/blocked requests).
3. **Site-compat corpus** (top 100 sites + the ones users report, e.g. Google Workspace, Meet, Figma, Teams, banking): WKWebView with Search's UA fix vs Chrome. Count functional breakages.
4. **Head-to-head memory/CPU:** N=1, 5, 20 tabs and 1/5 profiles for WKWebView vs CEF (Chrome-style) vs Helium, using `footprint`; the missing Chromium side of Q5.
5. **FairPlay end-to-end:** Netflix, Disney+, Spotify, Apple TV+, Prime Video in an ad-hoc and a Developer-ID-signed WKWebView app; record maximum resolution, HDCP behaviour, errors.
6. **Passkeys without and with the entitlement:** run webauthn.io registration/assertion, conditional mediation, security key, phone QR; confirm what `isUVPAA` false means in an unentitled app; and the AuthenticationServicesAgent wedge Search describes.
7. **Overlay composition on the current GPUI** with a `WKWebView` child: slide-in panel, hit-testing, first responder, full screen (`gpui.md` U1–U6, U8 apply directly).
8. **Hidden/occluded `WKWebView` throttling** and discard fidelity: timer rate, `visibilityState`, audio, `interactionState` restore of scroll, forms; Meet-style call exemption.
9. **Rust protocol implementation:** a `WKWebExtensionControllerDelegate` + `WKWebExtensionTab/Window` implemented with `objc2` `define_class!` and the load of a real CRX; the measure is lines of Rust versus Search's Swift.
10. **Adaptive Dark Mode / `WKWebView` exposure** of WebKit 27.3 features, and whether WKWebView users get Safari-27.x features on macOS 15.
