## Headline findings

1. **Correction to `cef.md`:** stock CEF 156.0.30 (Spotify build) **does** get Widevine. The CDM is fetched by Chromium's component updater into `<root_cache_path>/WidevineCdm/<ver>/` within ~1-2 min of first launch; my earlier probe ran too early. Observed: after that, `requestMediaKeySystemAccess('com.widevine.alpha')` succeeds (VP9/WebM, `SW_SECURE_DECODE`), and Shaka played a Widevine-encrypted VP9 stream for 9.5 s (241 frames, 0 dropped). It survived a restart. [35]
2. **But it is not production-grade DRM:** stock CEF ships no VMP `.sig` files; castLabs' VMP Lab returned `PLATFORM_TAMPERED` (VMP on, signatures missing). castLabs says that on macOS/Windows production services "typically will not work". [28][35]
3. **H.264/AAC need `proprietary_codecs=true`, and with FFmpeg present that forces `ffmpeg_branding=Chrome`**, which compiles FFmpeg's H.264 and AAC decoders in. No stock flag combination gives "OS decoders only"; the maintainer-tested variant (assert patch) played H.264 video but not AAC audio. [7][8][12][16]
4. **There is no maintained third-party CEF-with-codecs distribution suitable as a dependency.** CEF's maintainer: "We don't provide builds with proprietary codecs due to licensing reasons." [17][31]
5. **Licence costs are small for H.264 and real for AAC/HEVC:** AVC is free for the first 100,000 units/yr (one legal entity); AAC has no free tier ($0.98/unit from unit 1); HEVC software is $1.00/copy (Region 1) less a $25k annual credit. Whether free downloads count as "units" is not stated on the pages. [18][19][20]
6. **Production Widevine needs VMP signing, which needs a Google agreement or castLabs 3PL**; castLabs' free EVS covers only unmodified castLabs-Electron builds. [28]

## 1. Proprietary codecs in CEF

### 1.1 Which flags, and where they are documented

- **CEF's own docs say nothing about codec flags.** A grep of every `docs/*.md` at branch 8078 for `proprietary|ffmpeg_branding|codec` returns no hits, including `branches_and_building.md`. **Observed** [1][2][3].
- The first-party statements are: Google's "CEF build instructions for Google products": "CEF's default build does not enable proprietary audio and video codecs … add the following to the GN_DEFINES environment variable: `ffmpeg_branding=Chrome proprietary_codecs=true` … these additional codecs require various licensing agreements with and fees paid to the individual codec patent holders" (**Observed**, fetched 2026-11-18) [5]; and CEF maintainer comments in issue #2009 (2016-10-05, same GN_DEFINES) and #3820 (2024-11-04, "We don't provide builds with proprietary codecs due to licensing reasons") (**Observed**) [17].
- Chromium `156.0.8078.96`, **Observed** [6][7][8][9][12]:

| GN arg | Default | Effect for Aeri |
|---|---|---|
| `proprietary_codecs` | `is_chrome_branded \|\| castos \|\| …` → **false** (`build/config/features.gni`) | Compiles MP4/AAC/AVC parsers (`media/formats/mp4/*`), H.264 Annex-B converters, `enable_hls_demuxer`, OpenH264 *encoder* (`media_use_openh264`). In `supported_types.cc`, **all** H.264/HEVC/MPEG-2/4/VC-1/Dolby Vision video and AAC/AC-3/E-AC-3/DTS/ALAC… audio are rejected when it is false, even if an OS decoder exists. |
| `ffmpeg_branding` | `Chromium` unless Chrome-branded | `media/BUILD.gn:90-94` asserts `!= "Chromium"` when `proprietary_codecs && media_use_ffmpeg`. FFmpeg `Chrome` config: `CONFIG_H264_DECODER=1`, `CONFIG_AAC_DECODER=1`, `H264_PARSER`, `AAC_PARSER`; `Chromium` config: both 0. Both configs: `MOV_DEMUXER=1`, `MP3_DECODER=1`, `HEVC_DECODER=0`. |
| `enable_platform_hevc` | `proprietary_codecs && (enable_hevc_parser_and_hw_decoder \|\| cast)` | HEVC demux; decode is platform-only (no FFmpeg HEVC decoder in either branding). |
| `enable_hevc_parser_and_hw_decoder` | `proprietary_codecs && (win \|\| apple \|\| android \|\| linux)` → **true by default on mac/win** once proprietary | HEVC through VideoToolbox/D3D11. Set `false` to keep HEVC out. |
| `enable_platform_ac3_eac3_audio` | false on desktop | Dolby audio only if set explicitly. |
| `enable_widevine` | false unless Chrome-branded | **CEF forces `true`**, plus `enable_cdm_host_verification`, `enable_cdm_storage_id`, `enable_rlz` on mac/win and a fixed default `alternate_cdm_storage_id_key` (`tools/gn_args.py`, `BUILD.gn`, @8078) [4]. |

- Also **Observed**: the Spotify build already has MP3 ("probably"), VP9, AV1, Opus; H.264, HEVC, AAC, MSE H.264/HEVC all negative (`canPlayType` `""`, `isTypeSupported` false) [35]. The stock framework binary (238 MB) contains no `ff_h264_decoder`, `ff_aac_decoder` or `MP4StreamParser` symbols; the third-party codec build contains `ff_h264_decoder`, `ff_aac_decoder` and 26 `MP4StreamParser` hits and no `ff_hevc_decoder` (consistent with the gni; binary sizes are not comparable). [35]

### 1.2 Does `automate-git.py` take these flags?

Yes, through the `GN_DEFINES` **environment variable**, not a CLI option. `tools/gn_args.py` merges `GN_DEFINES` with CEF's required values and rejects conflicts; `proprietary_codecs`/`ffmpeg_branding` are not on CEF's required list, so they pass through (**Observed**, @8078 [4]). CEF's macOS recipe: `GN_DEFINES=is_official_build=true`, `CEF_ARCHIVE_FORMAT=tar.bz2`, `automate-git.py --download-dir=… --branch=8078 --arm64-build --minimal-distrib --client-distrib --force-clean --no-chromium-history --with-pgo-profiles` (**Observed** [2]); `--no-debug-build` skips the Debug build (flag exists, `automate-git.py:939`). Working third-party examples use `GN_DEFINES="is_official_build=true proprietary_codecs=true ffmpeg_branding=Chrome chrome_pgo_phase=0 dcheck_always_on=false"` (**Reported**, native-browser `build-cef-codecs.sh`) [31]. Use the newest master `automate-git.py` even for release branches [1].

## 2. Prebuilt CEF with codecs

- **No general-purpose maintained distribution exists.** Spotify's index and `cef-builds.spotifycdn.com` are stock (`proprietary_codecs=false`) [1][31]. CEF's maintainer (2024-11-04): they do not provide codec builds [17].
- Third-party artifacts I found (all **Observed** unless noted):
  - `agentmuxai/cef` releases: `cef-macos-arm64-156.0.8078.88-codecs-r2` (197 MB, 2026-11-12), Linux codecs build, a Windows zip not labelled "codecs". A fork of CEF carrying that app's patches; the macOS framework is **ad-hoc signed, no Team ID, not Developer-ID/notarised** (`codesign -dv`); version trails stock (`.88` vs `.96`/`.100`). Static check: contains `ff_aac_decoder`/`ff_h264_decoder`. Provenance, licence stance and update promises: none stated. App-specific, not a product.
  - `Glass-HQ/cef-builds` (a GPUI+CEF browser, "custom CEF 146 … proprietary codecs (H.264, AAC, Widevine)"): **Reported** from a search snippet; the repo/PR returned 404 to me.
  - `dsh0416/cef-automated-builds`: workflow only, no releases, failing (above). `tinyhumansai/openhuman` and `mhplala/native-browser`: build scripts, binary deliberately not hosted ("carries license obligations") [31].
- Commercial/adjacent (not CEF): **Electron** ships Chrome-branded FFmpeg; **castLabs ECS** adds Widevine/VMP (Electron only) [28]; **JxBrowser** disables H.264/AAC/HEVC by default, requires you to hold the licences, and says "Patent holders do not license codecs to the software that represents only a part of the final product" [31].
- Security-update trust: **Inferred**: none of the above has a published update SLA or signed provenance; a dependency on them would put an unaudited ~500 MB native binary in Aeri's sandbox boundary. Building from `chromiumembedded/cef` source yourself is the only auditable route.

## 3. OS decoders instead of FFmpeg

**What Chromium 156 can do natively (Observed [9][10][11]):**
- macOS video: `VideoToolboxVideoDecoder` (GPU process). Chromium parses H.264 itself (`H264Decoder` + `VideoToolboxH264Accelerator`) and hands slices to VideoToolbox. Profiles Baseline-High, **hardware only** (`VTIsHardwareDecodeSupported`). HEVC (under `enable_hevc_parser_and_hw_decoder`) allows "the OS software decoder".
- Windows video: D3D11/DXVA hardware decoders (`gpu_mojo_media_client_win.cc`); HEVC under the same flag. Not read in depth.
- **AAC-LC has no platform path.** `AudioToolboxAudioDecoder` is xHE-AAC only (comment: "We use AudioToolbox for decoding xHE-AAC"; `CHECK_EQ(profile, kXHE_AAC)`); the Windows MF decoder is registered for xHE-AAC on Win11 22H2+ only. The renderer's audio decoder list is `FFmpegAudioDecoder` (+ the external/mojo factory). So AAC-LC decode is FFmpeg's AAC decoder.
- `proprietary_codecs=true` is required even for platform-only decode (supported-types gate above), and with `media_use_ffmpeg=true` it forces `ffmpeg_branding=Chrome`.

**Can you avoid shipping FFmpeg's H.264 decoder? Not with flags.** CEF issue #3559 "Enable proprietary codecs with OS decoding support only" (opened 2023-08-24, **still open**, last activity 2026-06-01) [16]:
- Maintainer's patch (`media/BUILD.gn`: skip the branding assert when CEF is enabled) + `proprietary_codecs=true` without `ffmpeg_branding=Chrome`. Result on macOS 13.5.1 and Windows 10, M117: **H.264 video plays, AAC audio does not** ("FFmpegDemuxer: skipping invalid or unsupported audio track"). **Reported** (maintainer test, 2023).
- Hardware only: devices lacking HW decode cannot play; `--disable-accelerated-video-decode` proves no software path. FFmpeg's AudioToolbox/MF options did not fix AAC; Chromium's own `mp4/aac.cc` parsing would also need OS replacement (maintainer, 2023-08-28). The patch did not land: the assert is intact at 156.0.8078.96 and CEF's patches. **Observed** [7][16].
- **Vivaldi's route:** "Because of patents Vivaldi cannot ship with certain codecs turned on in ffmpeg (the AAC audio codec and the h264 video codec as of 09.2022)", so Mac and Windows use platform decoders via a `platform_media/` patch set inherited from Opera (own `media::VideoDecoder`s, FFmpeg-interface AAC decoders wrapping OS APIs, sandbox changes, a patched VideoToolbox decoder that allows software decode); on Linux the user installs another FFmpeg. Vivaldi estimates the last H.264 patent expires "around 2027" and that FFmpeg's AAC parts date from 2003 or earlier (their belief). **Observed** in the mirrored source (`ric2b/Vivaldi-browser`, `platform_media/` present on master, pushed 2025-12-01); **Reported** as Vivaldi's legal position [24].
- **Firefox:** Gecko decodes through the OS: `AppleDecoderModule` (VideoToolbox for H.264/VP9/AV1/HEVC; `AppleATDecoder`/AudioToolbox for `audio/mp4a-latm`) and `WMFDecoderModule` (`CLSID_CMSH264DecoderMFT`, `CLSID_CMSAACDecMFT`) (**Observed**, gecko-dev master 2026-11-18 [22]). Brendan Eich (Mozilla CTO, 2013-10-30): "Firefox already supports H.264 for the video element using platform codecs where they are available" [21]. Apple, Microsoft, Google and Cisco are on Via LA's AVC and AAC licensee lists (also Valve, Spotify, Netflix on the AVC list); **Mozilla does not appear on either list** (Observed, grep of the pages fetched 2026-11-18) [18][19].
- **Inferred legal reading:** the "OS vendor holds the licence" argument is strongest when the app contains no decoder implementation. A Chromium-based Aeri still carries Chromium's own H.264 parser/DPB (`H264Decoder`) and MP4 demuxers, so the exposure is smaller than option A but not zero. Ask counsel; the AVC licence has a separate OS-bundled category that an app is not in [18].

**Cost of "platform-only" for Aeri (Inferred):** a maintained patch set (assert, AAC via AudioToolbox/MF, software fallback decisions, demuxer paths). Vivaldi/Opera carry this as a directory; CEF upstream has declined for 3+ years.

## 4. Patent licensing (Via LA, Access Advance)

### 4.1 AVC/H.264 (Via LA; page modified 2026-11-11) [18]
- **PC software, "Section 1 – Codec Manufacture and Sales"** (decoder/encoder/both = 1 unit): units 1-100,000/yr **$0.00** ("available to one legal entity in an affiliated group"); 100,001-5,000,000 **$0.20**; >5,000,000 **$0.10**; enterprise cap **$9.75M/yr** (2017 on). Same table for products incorporated into a PC OS. Covers end-user personal/consumer/internal-business use. Observed.
- **Who signs:** the licensee is the entity that makes/sells the end product incorporating the codec; end users are covered by it. A separate **Section 2 streaming** schedule (title-by-title, OTT/FAST/social/cloud-gaming tiers, e.g. $100K for small, $4.5M for 100M+ subscribers) applies to **content services**, not to a browser; it replaced the old "Internet Broadcast: no royalty" rule in 2026 (reported by Tom's Hardware/TechSpot). Observed on the page; **Reported** for the change history [18].
- Licence mechanics: sign with Via LA, report units; the FAQ warns users "may have to negotiate licenses for essential patents that are not included". Illustration (Inferred arithmetic): 1M units/yr ⇒ 900,000 × $0.20 = $180,000. **Unknown:** whether free downloads of an open-source browser are "units".

### 4.2 AAC (Via LA; page modified 2026-10-01) [19]
- Standard worldwide rate, **no free tier**: units 1-500,000 **$0.98**; 500,001-1M $0.78; 1-2M $0.68; 2-5M $0.45; 5-10M $0.42; 10-20M $0.22; 20-50M $0.20; 50-75M $0.15; >75M $0.10 (>2 channels = 1.5 units). Alternative R1/R2 table: R2 starts at $0.64. Observed.
- One-time initial fee **$15,000**; **$1,000 for "small entities" (≤15 employees and <US$1M gross revenue)**; quarterly unit reports; 30-day trial allowance; the FAQ says "PC Software pricing remains available for products that have been approved by Via LA for reporting in this category" (rates not published). Licensee signs the AAC Patent License Agreement; Google does **not** cover Android OEMs, i.e. embedders pay their own [19].
- Illustration (Inferred): 100,000 units ⇒ $98,000 + initial fee at the standard table. Ask Via LA for the PC-software table and whether free copies count.

### 4.3 HEVC
- **Access Advance** "HEVC Advance Program Overview" (July 2026), Observed [20]: licenses HEVC decoders/encoders "whether made available in devices, software or through Cloud Based Services"; royalties due for "HEVC Software Sold separately from a device". **HEVC Software rate: $1.00 (Region 1: US/EU/UK/Japan…) / $0.50 (Region 2)** with the in-compliance + logo discount; $1.111/$0.555 without logo; **$1.333/$0.667** standard; annual enterprise credit **$25,000** (four $6,250 instalments) for in-compliance licensees that owe royalties; first term to 2030-12-31 with 20% renewal cap. The programme states it focuses on parties that "Sell … devices or software". Via LA's HEVC/VVC programme was **acquired by Access Advance on 2025-12-15** (page notice) and is run by its subsidiary Video Codec Licensing LLC; a Duplicate Royalty Policy exists for dual licensees [20].
- Illustration (Inferred): 100,000 Region-1 copies ⇒ $100,000 − $25,000 credit = $75,000. Chrome ships HEVC only through platform decoders ("hardware decoding … where available", Chrome 107; chromium.org: "requires hardware support") [15][34]. **Inferred recommendation:** compile HEVC out (`enable_hevc_parser_and_hw_decoder=false enable_platform_hevc=false`) until counsel decides whether OS-decoder-only HEVC needs a licence.

### 4.4 What Chromium-based OSS browsers do (flags Observed; licence status mostly undisclosed)
- **Brave** (company): `build/args/blink_platform_defaults.gni` sets `proprietary_codecs = true`, `ffmpeg_branding = "Chrome"`, `enable_widevine = true`, and explicitly enables HEVC ("Since Brave enables proprietary_codecs…") [23]. No licence statement in the files.
- **ungoogled-chromium** (volunteers): `flags.macos.gn` (ungoogled-chromium-macos), `flags.windows.gn`, and `debian/rules` all set `ffmpeg_branding="Chrome"` + `proprietary_codecs=true`; core `flags.gn` leaves them unset; no patent statement in its FAQ (grep). A third-party catalogue claims official ungoogled builds are "open codecs only" (**Reported**, conflicts with the packaging flags) [25].
- **Helium** (`imputnet/helium-macos`): `flags.macos.gn` = `ffmpeg_branding="Chrome"`, `proprietary_codecs=true`, `enable_mse_mpeg2ts_stream_parser=true`; Widevine: see §5 [26]. **Thorium**: README advertises FFmpeg HEVC/AC-3/E-AC-3 and "Widevine integration where … redistribution is permitted"; no patent statement found [27].
- **Vivaldi/Opera:** OS decoders (above). **Google Chrome:** Google is on Via LA's AVC and AAC licensee lists [18][19]; chromium.org labels H.264/AAC/HEVC "Limited to Google Chrome" [15]; a catalogue site adds that Google's licence "does not extend to anyone else compiling Chromium" (Reported) [25].
- **Inferred:** volunteer projects ship the codecs and carry the legal exposure themselves; the only documented licensing-driven design choices are Vivaldi's OS decoders and Mozilla's OpenH264/OS decoders.

### 4.5 Firefox / OpenH264 [21]
- Cisco's `BINARY_LICENSE.txt` (Observed): the Cisco binary is licensed under Cisco's AVC licence "at no cost to you" **only if** (1) it is "separately downloaded to an end user's device, and not integrated into or combined with third party software prior to being downloaded", (2) the user can enable/disable it, (3) the UI shows "OpenH264 Video Codec provided by Cisco Systems, Inc.", (4) the EULA repeats the notice. FAQ: a team that builds the source "is responsible for paying all applicable license fees"; Cisco covers only MPEG LA royalties for its binary, no guarantee about other patent holders.
- MozillaWiki (Observed): OpenH264 is used since Firefox 33 for WebRTC, "not packaged with Firefox; it is downloaded and updated from Cisco's servers"; "OpenH264 is for WebRTC only … it doesn't enable playing back MP4 videos". Eich (2013): "Cisco will pay for the patent license from the MPEG LA. Firefox will automatically download and install the appropriate binary module".
- **Inferred:** OpenH264 does not solve `<video>` H.264 or AAC, and Chromium's own compiled-in OpenH264 *encoder* (`media_use_openh264` when proprietary) is not Cisco's downloaded binary, so it gets no Cisco coverage.

## 5. Widevine

### 5.1 What a non-Google Chromium embedder gets (Observed in source and probe)
- Chromium: `enable_widevine` default is Chrome-branded/Android only; the comment says "Can be optionally enabled in Chromium on non-Android platforms. Please see //src/third_party/widevine/LICENSE" (`widevine.gni` @156). `registration.cc` registers `RegisterWidevineCdmComponent` when `ENABLE_WIDEVINE_CDM_COMPONENT`, which CEF forces [13][4].
- CEF history (all Observed): #1631 (2015) CDM support added, maintainer: "You can't distribute the Widevine binaries yourself without a license"; #2009 (2016) `CefRegisterWidevineCdm()` added; #3149 (2021-06/08) component-updater download restored in M93 ("going forward, update of the CDM during runtime will only be supported via the Component Updater"; CDM lands under `<user_data_path>/WidevineCdm`; `--disable-component-update` turns it off); #3404 (2022-10) CDM host verification + storage ID added, enabled only when `.sig` files exist; #3952 (2025-06) Windows bootstrap `.sig` fix [17]. No `RegisterWidevine` API exists at 8078 (grep). CEF 156 adds `CefComponentUpdater` (API 14600: `GetComponentByID`, `Update(id, priority, callback)`) for on-demand updates; the Widevine component id is `oimompecagnajdejgnnjijobebaeigek` (in Helium's allowlist patch and in a castLabs issue log) [4][26][30]. The `CefComponentUpdater` call itself was not exercised in my probe (the component arrived through Chromium's own scheduler).
- **My probe (CEF 156.0.30, macOS arm64, Spotify build, no `.sig`)**: CDM `4.10.3112.0` (`libwidevinecdm.dylib` 20.4 MB, mac_arm64; manifest `x-cdm-codecs: vp8,vp09,avc1,av01`, `x-cdm-persistent-license-support: false`, schemes `cenc,cbcs`; `update_url` `clients2.google.com/service/update2/crx`) appeared ~1-2 min after first launch; Shaka playback worked; `HW_SECURE_ALL` and any `avc1` configuration rejected; `SW_SECURE_DECODE` accepted (L3-class); VMP Lab: `>> LICENSE_REQUEST | CDM 4.10.3112.0 << LICENSE | PLATFORM_TAMPERED`; UA client hints brands = `Not:A-Brand`, `Chromium` (no "Google Chrome"); UA string `…Chrome/156.0.0.0 Safari/537.36`. [35]
- The CDM licence text (shipped in the component and in Chromium's `third_party/widevine/LICENSE`): "You may not use, modify, sell, or otherwise distribute the Software without a separate license agreement with Google. The Software is not open source software." **Observed** [13][35]. Google's Widevine overview: "A license agreement is required for the use of Widevine products or services. Widevine does not assess any fee for use of its products and services", and lists "Chromium Embedded Framework (CEF) / Electron" as supported [29].
- **Inferred:** with the component updater, Aeri never redistributes the CDM (the user's browser fetches from Google), which is how stock CEF, JxBrowser and unlicensed Chromium forks operate, but the licence wording covers *use*. Treat DRM as unlicensed until Aeri has a Google agreement.

### 5.2 Licence application and VMP
- **Google agreement:** no public application form; Widevine's contact page routes to a support troubleshooter [29]. Helium's maintainers say Widevine certification costs "ten thousand+ dollars" and that they would need to ask Widevine for a licence (**Reported**, issue #116, 2025-09-26; #2389 2026-08-25: "nothing … has changed") [26]. A forum post says Vivaldi pays nothing because it is a company (**Reported**, third-hand) [26].
- **VMP (Verified Media Path):** castLabs: "Many premium content streaming services will deny DRM license requests if a VMP isn't present"; "Previously a license agreement with Google Widevine was required to get your own VMP signing certificate" [28]. Status meanings (Observed [28]): `PLATFORM_UNVERIFIED` = VMP off, "On macOS/Windows this means production streaming services will typically not work"; `PLATFORM_TAMPERED` = VMP on, signatures broken/missing, "Production playback will likely fail". My unsigned stock-CEF probe reported **TAMPERED** (Observed). CEF's #3404 says host verification is only enabled at runtime "if valid sig files exist", which would predict UNVERIFIED; the mismatch is unexplained (Unknown, see spike 1). Either status is a failing state for production services on macOS/Windows per castLabs.
- **Where CEF looks for signatures (Observed, `cdm_host_file_path.cc` @8078 [4]; #3404 [17]):** macOS `Contents/Resources/<name of the current process executable>.sig` (#3404: `<AppName> Helper.sig` for the helper) and `Chromium Embedded Framework.framework/Resources/Chromium Embedded Framework.sig`; Windows `<exe>.sig`, `<exe-name>.dll.sig`, and `libcef.dll.sig`. Only existing files are listed. castLabs: on macOS VMP-sign **before** code-signing, on Windows **after**; the app needs the `com.apple.security.cs.disable-library-validation` entitlement to load the CDM [28].
- **castLabs (Google "3PL" partner, `3pl@castlabs.com`):** EVS is "a free service, but requires signup" and only signs "unmodified ECS release binaries" or those with a fixed fuse set; "commercial VMP certification of custom Chromium/Electron adaptations" needs an audit by castLabs, after which 3PL access to EVS signs your custom builds; price unpublished. castLabs lists "Chromium, Electron, Firefox" as supported frameworks, **not CEF by name**, but a CEF build is a custom Chromium adaptation (**Inferred**) [28].
- **Brave** (Observed [23]): "Brave's licensing agreement for Widevine forbids distribution of Widevine's binaries" so its component server redirects to Google's; Brave ships `.sig` files ("Streaming services only offer high definition content to clients that are trusted") and builds with `ignore_missing_widevine_signing_cert=False`. **Vivaldi**: Widevine arrives through `vivaldi://components` "Check for updates" [24]. **Helium**: "does not currently have widevine"; Netflix fails, Spotify "works for maybe 1/3 of songs" with a Chrome-copied CDM (**Reported**) while its allowlist patch permits the Widevine component [26]. **ungoogled-chromium**: manual copy of Chrome's CDM + `--enable-widevine` [25].

### 5.3 Limits without VMP
- Not published by Google. Observed: only L3-class software sessions on macOS; no persistent licences (CDM manifest, castLabs: persistent support removed in browsers by M148). **Reported/Inferred:** production services refuse licences to unverified macOS/Windows clients, so the practical limit is "does not play", not "plays at SD". Netflix's own Mac table: Safari up to 4K, Chrome 1080p, Firefox/Opera 1080p, Edge 720p, and no row for any other browser (Observed) [30].
- UA/brand: castLabs issue #142 (2022, **Reported**): Disney+ gave code 83 "unless you specifically set the user agent to Chrome". The 156 UA already says Chrome (Observed); client-hint brands lack "Google Chrome".

### 5.4 Does any CEF-based app ship Widevine today?
Every app on Spotify CEF builds with the updater enabled fetches the CDM (Observed). I found **no CEF app with documented production VMP signing**. Reported but unverified: Glass (above). Non-CEF: castLabs ECS (VMP-signed Electron), JxBrowser (`engine.widevine().activate()` on Windows/macOS, "governed by its own terms of use"), Brave/Vivaldi/Edge/Opera (Chromium forks with their own agreements) [28][31].

## 6. Fallback UX when DRM is unavailable

- **Netflix** (Observed, Help Center node 27451): "Pardon the interruption. We're having trouble playing Netflix. Please visit chrome://components, find 'Widevine Content Decryption Module' and click on the 'Check for update' button." (M7701-1003) and "If you get this error but don't use Google Chrome, or you're using a Chromium-based web browser, your browser isn't supported by Netflix." Supported list: Chrome, Edge, Firefox, Opera, Safari [30]. Helium users also see "Please visit chrome://settings/content/protectedContent …" (Reported [26]).
- **Spotify web** (Reported, Spotify Community and Brave Community 2025-05-18): "Playback of protected content is not enabled." Supported browsers: Chrome, Firefox, Edge, Opera, Safari (Observed, support.spotify.com) [30].
- **Disney+** (help.disneyplus.com articles seen via search; host unreachable from my machine): "Digital Rights Management not enabled" (PB_WEB_PL-…) and "Your browser is no longer supported … Please enable DRM and try again" (PB_WEB_PL-3016-003); browser list Chrome, Firefox, Edge, Opera (Reported) [30].
- **Pattern:** all three show a generic error that tells the user to fix Chrome settings that do not exist in Aeri. Aeri should intercept this itself.
- **Clean "open in system browser" (Inferred design, APIs Observed):** (1) site list (netflix.com, disneyplus.com, primevideo.com, max.com/hbomax.com, open.spotify.com playback, tv.apple.com …) matched in `CefRequestHandler::OnBeforeBrowse`/`OnOpenURLFromTab`/`CefLifeSpanHandler::OnBeforePopup` (all exist in `include/` @8078); (2) a non-blocking page banner or toolbar chip, not a silent redirect; (3) macOS `NSWorkspace.open(_:)` ("Opens the location at the specified URL", all threads) or `open(_:withApplicationAt:configuration:completionHandler:)` (macOS 10.15+) to target a specific browser [33]; (4) if Aeri is the default browser, `open` would loop back, so resolve another handler for https (e.g. `urlsForApplications(toOpen:)`, not fetched) or let the user pick once; (5) remember the choice per site; (6) detect actual failure (EME probe in the page's main world or the service's error page) before offering it, so DRM keeps working where it works.

## Recommendation

**First usable release (E + D0, stock CEF):** ship the stock Spotify CEF pinned in cef-rs (no custom Chromium yet); keep the component updater on and trigger/await the Widevine component at first launch (CEF `CefComponentUpdater`, API 14600) so EME probes pass; **do not advertise DRM**. Add the site-list handoff to the system browser (§6) for Netflix, Disney+, Prime Video, Max, Spotify web playback and Apple TV/Music, with a visible "Open in <default browser>" action and a per-site remembered choice. Communicate the H.264/AAC gap openly (X/Twitter, many news players will not play). Build a private codec-enabled CEF for the owner's own machines only (option A, never distributed) to validate behaviour and the build pipeline. No licence needed while nothing is distributed with codecs (**Inferred**, confirm with counsel).

**Beta (A, with D started):**
1. Stand up a reproducible CEF build on a dedicated Apple Silicon Mac (≥32 GB RAM, ≥500 GB SSD, persistent git and ccache; self-hosted runner), tracking the CEF **Extended** branch to cut rebuilds to ~8-weekly with monthly cherry-picks, e.g. `GN_DEFINES="is_official_build=true proprietary_codecs=true ffmpeg_branding=Chrome enable_hevc_parser_and_hw_decoder=false enable_platform_hevc=false alternate_cdm_storage_id_key=<Aeri's own>"` with `automate-git.py --arm64-build --no-debug-build --minimal-distrib --client-distrib --with-pgo-profiles`. Windows x64 build on a Windows host afterwards.
2. Before any public codec build: have counsel confirm and then sign the Via LA AVC licence (free ≤100,000 units/yr, one legal entity) and AAC licence ($1,000 initial if Aeri's entity is ≤15 people and <$1M revenue, else $15,000; $0.98/unit; ask for PC-software pricing and whether free copies count). **Leave HEVC off** until counsel rules on OS-decoder-only HEVC; if wanted, the Access Advance figure is $1.00/copy less the $25k credit. Ship notices/credits with the app.
3. **DRM:** start the castLabs 3PL inquiry (`3pl@castlabs.com`) and a Google Widevine agreement request as **long-lead items at the start of beta**, in parallel with the codec work; both depend on a stable custom build. Until VMP exists, keep option E for DRM sites. If the Google/castLabs path is refused or too costly, stay on E; Aeri then ships H.264/AAC but no production DRM, which still covers social and news video.
4. Run the platform-decoder spike (option B) only as a licence-cost hedge, not on the beta critical path.
